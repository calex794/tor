# TOR S3-34 — безопасный переход новых платных глав на KEK V2

Статус: инструкция для разработки и изолированных испытаний. **Не означает,
что производственная смена ключа выполнена.** Рабочий VPS не изменяется
автоматически, а любой операторский запуск требует отдельно подтверждённого
плана восстановления.

## Существующие гарантии

- Договор платного чтения: [paid-delivery-v1](../contracts/paid-delivery-v1.md).
- Каждая редакция имеет свой уникальный DEK и собственный неизменяемый
  S3-шифротекст. Хранится только зашифрованная оболочка DEK.
- V1 и V2 обозначают идентификаторы **KEK**, а не редакции книги. Редакции
  книги V1/V2 в B могут независимо использовать любую допустимую версию KEK.
- Ключи V1 и V2 — два независимых 32-байтовых секрета. Не выводить V2 из V1,
  cookie/JWT, БД или другого общего секрета.

## Выбор активного ключа

В G новые публикации вызывают `seal_chapter_with_keyring`, затем
`PgStorageRegistry::reserve_pending_with_keyring`. Старый интерфейс
`seal_chapter` / `reserve_pending` остаётся строго V1 для обратной
совместимости: он **никогда** не переключается автоматически.

- `TOR_CONTENT_KEK_V1` — обязательный секрет для исторических редакций.
- `TOR_CONTENT_KEK_V2` — отдельный необязательный секрет чтения V2.
- `TOR_CONTENT_ACTIVE_KEK_ID` — `content-kek-v1` или
  `content-kek-v2`. Если переменная отсутствует — новые G-публикации
  используют V1. Неверное/пустое значение или V2 без ключа V2 — отказ
  до создания новой главы. Запрещён незаметный возврат к V1.

Выбор ключа производится только на сервере, не из параметров HTTP или
поля формы автора. Изменение активного ID не перешифровывает уже купленные
главы. G выдаёт DEK читателю только по проверенному идентификатору из
сохранённой строки attached и после разрешения D/B.

## Порядок испытаний перед операторским включением

1. Подготовить согласованные независимые резервные копии PostgreSQL, S3
   и обоих секретов KEK. Проверить восстановление на другой площадке.
2. Протестировать чтение старой купленной V1 с обязательным KEK V1 и новым
   ключом V2 в окружении без переключения активной версии.
3. В изолированной среде включить V2 для **новых** публикаций, выполнить
   G: seal -> pending -> S3 PUT+GET+hash -> ready; B: связать редакцию с
   объектом и опубликовать; D: подтвердить купленное право на старую V1.
   Проверить чтение новой редакции и исторической купленной V1.
4. Проверить отказ без V2, при ошибочном V2, неверном active ID, подмене
   object/AAD/hash, несоответствии роли и недоступном S3. Не возвращать
   ни plaintext, ни KEK, ни DEK при отказе.
5. После выпуска нового V2 **не удалять V2 при возврате активного ID на V1**.
   Откат выборки для новых публикаций не откатывает уже созданные
   зашифрованные главы; сохранение обеих версий KEK для чтения обязательно.
6. Не выводить V1 из использования до отсутствия ВСЕХ ссылок на него
   (включая pending, ready, attached), проверки копий, прав покупки
   и успешного восстановления каждой исторической редакции.

## Технические ограничения

Эти изменения добавляют серверные функции G и проверки B/G; они не создают
новый публичный маршрут авторской публикации и не запускают пакетное
перешифрование. Смена активного ключа на рабочем VPS, массовый rewrap,
отзыв старого секрета и физическое размещение резервной копии требуют
отдельного решения, проверки и процедуры оператора.
