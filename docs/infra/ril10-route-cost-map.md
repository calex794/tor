# TOR / RIL-10 — карта затрат маршрутов (первая реализация)

Владелец: I-09. Данные собирает G через RIL-06, классификацию маршрутов ведёт I. **RIL не принимает решения об оплате, правах, блокировке, рекламе или ранжировании книг.** Эта карта предназначена только для диагностики производительности сайта.

## Что реально измеряется

Из уже действующих `ril_route_hourly` (не более 30 суток хранения) фоновая, только читающая операция `PgRilRollups::read_cost_buckets(days)` получает сумму запросов по 15 конечным кодам, 6 группам статуса и 4 интервалам времени ответа. Параметр `days` — только 1…30; SQL использует параметры, не пользовательские URL. Максимально 360 строк. Никакого SQL в цепочке отдельного HTTP-запроса.

Чистая модель [`cost_map.rs`](../../crates/route_intelligence/src/domain/cost_map.rs) строит список маршрутов по **нижней границе суммарного времени ответов** (миллисекунды), с числом HTTP-ошибок, количеством медленных запросов и оценкой интервала p95. Сортировка воспроизводима; при равных суммарных границах учитывает количество ошибок и нагрузку. Система чётко различает сумму запросов и число пользователей. Состояние и метки ограничены фиксированными типами, без ID книг, людей, сессий, cookie и URL.

* Интервалы: менее 10 мс → минимум 0 мс; 10–99 мс → 10 мс; 100–999 мс → 100 мс; 1000 мс и больше → минимум 1000 мс и **неизвестная верхняя граница**.
* p95 — **интервал**, а не точное значение. При попадании в самую медленную группу верхняя граница отсутствует.
* **Обращения к PostgreSQL на отдельный HTTP-маршрут, фактическое время SQL, CPU, расход ресурсов и денежная цена здесь не измеряются.** Поля `db_queries`, `db_time_ms` и `monetary_cost` имеют значение `None`, а не обманчивые нули. Сортировка — по времени *ответов*, не по фактическим денежным расходам. Следующим независимым подшагом нужны безопасные счётчики SQL на стороне I/G с подтверждённым методом привязки к маршруту.

## Пользовательский путь и испытания

- Внутренний вызов без внешнего HTTP: `tor_web::ril_cost_map_for_diagnostics(&catalog, days, limit).await` возвращает `Option<Vec<RouteCostRanking>>`. Нет доступа публичных пользователей к отчёту, нет нового внешнего URL. При сбое PG возвращает `None`, а не ложную оценку нулевых затрат. Административное отображение — отдельный RIL-13.
- Чистые испытания: два маршрута с различной нагрузкой/временем, HTTP-ошибки, p95 и открытый медленный интервал, переполнение, дублирующиеся или неправильные группы, детерминированность. Сверка кодов I/G закрепляет соответствие всех 15 категорий маршрутов.
- [PostgreSQL 18](../../crates/traffic_behavior/tests/ril_costs_pg.rs): выборка до и после реальной атомарно обработанной пачки, повторное подключение, отказ для 0 и 31 суток, ограничение формы ответа. Испытание подключается к существующему `TOR PostgreSQL runtime`, без новой отдельной дорогой очереди.

## Условия закрытия RIL-10

В этом изменении закрывается **первый измеримый вариант**: относительная карта нагрузки/ошибок/времени за 1–30 суток. До полного принятия RIL-10 остаются измеренные расходы SQL/CPU, точное p95 (при необходимости), связь с действующим административным интерфейсом RIL-13 и испытание реального сервера. Не менять основную схему PG или права `tor_app` ради вспомогательного отчёта. Источник: [контракт RIL](../contracts/ril-platform-v1.md).
