# TOR: обязательная структура по функциональным областям

**Решение для чистовой разработки `calex794/tor`.** Один Git-репозиторий, один основной Axum-сервер, одна PostgreSQL. `bokarust` — испытательная основа, NEwBOO — эталон поведения. Перенос из них не отменяет этой структуры.

## Одна предметная область = собственные слои и тесты

```text
tor/
  Cargo.toml                       # Rust workspace
  architecture/modules.toml        # владельцы областей
  crates/
    contracts/                     # общие ID, узкие междоменные интерфейсы
    books/
      Cargo.toml                   # tor-books
      src/
        lib.rs                     # объявление модулей
        api/                       # HTTP-маршруты и валидация
        services/                  # сценарии и транзакционные границы
        repositories/              # SQLx и хранение
        schemas/                   # структуры входа/выхода
        domain/                    # сущности и правила
      tests/                       # тесты этой области
    reading/                       # свой набор api/services/repositories/...
    commerce/                      # свой набор api/services/repositories/...
    web/                           # объединение маршрутов и зависимостей
  migrations/                      # последовательные миграции через I
  tests/architecture/              # проверка архитектурных запретов
  docs/contracts/                  # спецификации API, событий, прав и лимитов
```

Не создавать пустые слои для вида. Новая область регистрируется в `architecture/modules.toml` вместе с единственным владельцем A–H; изменение реестра и общих контрактов координирует I. Запрещено дублировать один сервис в `src/services/` и `crates/books/src/services/`. Корневые `services/`, `repositories/` и `src/` исключены. У каждой реализуемой области собственный тест или модуль с тестами.

## Точная ответственность

- `api`: парсинг/проверка HTTP, входы/выходы, вызов сервиса. Без SQL и финансовых решений.
- `services`: операция и проверка бизнес-правил, составная атомарная транзакция. Не импортирует SQLx напрямую.
- `repositories`: запросы PostgreSQL, реализация узких портов, операции внутри переданной транзакции.
- `schemas`: типизированные структуры данных. Без SQL.
- `domain`: сущности/инварианты, без зависимости от Axum и SQLx.
- `contracts`: общие идентификаторы и узкие интерфейсы; без инфраструктуры. `web` связывает области в одном сервере, но не выполняет SQL.

Разработческие области не зависят напрямую друг от друга через Cargo, даже если зависимости не образуют цикл. Связь через `contracts` и реализацию при сборке приложения. Один источник записи на набор таблиц. Общая миграционная последовательность согласуется I. Деньги/журнал/выдача права на купленную версию — атомарно; прогресс чтения не выдаёт доступ.

## Цикл разработки и проверок

1. Одна законченная предметная ветка. При написании — дешёвая компиляция, форматирование и нужный критический защитный тест.
2. После завершения блока — собственные тесты, PostgreSQL/API/браузер по затронутой области, положительные и отрицательные случаи. Собирать все ошибки, исправлять группами, затем обязательно перепроверять весь набор области на финальном SHA.
3. При изменении общего контракта, маршрутизатора, ACL, денег и миграций расширить тесты; при неизвестном воздействии — полный безопасный набор. Интеграция проверяет общий реальный пользовательский путь, затем объединяет.
4. Нет результата «готово» без PostgreSQL, прав доступа, успешного пользовательского пути и ссылки на SHA/CI.

## Автоматические ограничения

`tools/check_feature_layout.py` запускается из **существующего** workflow `.github/workflows/rules.yml`. Он проверяет регистрацию Cargo-пакетов, собственные слои/тесты, запрет междоменных прямых зависимостей, SQLx вне repositories и Axum в domain. Предупреждение после 400 строк производственного кода / 800 тестового, запрет после 600 / 1000. Семантику и реальное покрытие проверяют дополнительные тесты и ревью — этот контроль не подменяет их.

Пока TOR содержит только документацию, отсутствие Cargo допустимо; добавление каталога `crates/` без workspace блокируется. Ветка `feat/bootstrap-from-bokarust` использует старые глобальные пакеты; перед интеграцией её код необходимо распределить по функциональным областям, а не ослаблять эти правила.
