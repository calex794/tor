## Рекомендуемые параметры при заказе

| Параметр | Рекомендация |
| --- | --- |
| ОС | Ubuntu 24.04 LTS (x86_64) |
| CPU | 2 виртуальных ядра для первых проверок; 4 предпочтительно для фоновых задач |
| RAM | 4 ГиБ для первой версии; 8 ГиБ с запасом |
| Диск | 50–80 ГБ NVMe/SSD + отдельное внешнее резервное хранилище |
| Сеть | Один публичный IPv4, исходящий HTTPS, входящие 22/80/443 по политике доступа |
| База данных | Отдельная база PostgreSQL на этом VPS, порт только на `127.0.0.1` |
| Приложение | Rust + Tokio + Axum, пользователь без root |
| HTTPS | Nginx + сертификат TLS для выделенного имени tor (домен пока не определён) |

Это **ориентиры**, не доказательство достаточной мощности. До установки снять `free -h`, `nproc`, `df -h`, проверить свободные порты и нагрузку. Никакой общей базы/диска с Chaptera или Эридой.

## Целевой путь выпуска

```text
A–I feature branches
      ↓   отдельные небольшие PR
tor/main (только проверенные изменения)
      ↓
GitHub Actions: Rust, PostgreSQL, браузер, права, миграции
      ↓
Сборка пакета с точным commit SHA + SHA-256
      ↓
SSH от выделенного пользователя → /opt/tor/releases/<SHA>
      ↓
Запуск кандидата на loopback + отдельной тестовой БД
      ↓
Проверка /healthz, /readyz, HTTP, реальный браузер
      ↓
Атомарное переключение /opt/tor/current + systemd
      ↓
Nginx HTTPS → испытательный сайт, видимый владельцу
      ↓
Проверка установленного SHA; при ошибке откат приложения
```

**Текущее требование (28.10):** изменения в `tor/main` никогда не меняют VPS автоматически. Для обычного выпуска запускается `tor-one-click-release.yml` на ветке `main`, без ввода SHA и без переключателей; вся проверка, локальная резервная копия базы, миграции, установка и проверка отката происходят внутри одного задания. После одноразовой настройки пользователя `tor-deploy` правами root обладает только установленный root-владельцем `/usr/local/sbin/tor-one-click-release`. Если текущий сайт уже неисправен, установка отказывается продолжаться. Автоматического отката SQLx нет — копия базы сохраняется отдельно. Ветки/непроверенные PR **никогда** не имеют доступ к ключам VPS. Если проверка не прошла, предыдущая рабочая версия остаётся.

## Одноразовая подготовка после выделения VPS

1. Подтвердить принадлежность сервера к проекту `tor`, ОС, CPU/RAM/диск, SSH-адрес/порт, выбранный домен и отпечаток SSH host key по независимому каналу.
2. Создать ограниченного пользователя `tor-deploy` и каталоги `/opt/tor/releases`, `/opt/tor/current`, `/var/lib/tor`; сервис `tor-web.service` от отдельной учётной записи без root. Не давать SSH ключу полномочия изменять произвольные systemd службы.
3. Установить PostgreSQL с отдельными пользователем/БД и безопасными ролями мигратора. Не публиковать порт 5432. Данные базы и секреты хранятся **вне** каталогов релизов.
4. Подготовить отдельный тестовый адрес HTTPS и Nginx vhost, слушать приложение только на loopback. До беты ограничить доступ к тестовому сайту и добавить `X-Robots-Tag: noindex, nofollow`.
5. Настроить GitHub Environment `tor-staging` и защищённые секреты `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `SSH_KNOWN_HOSTS` (и при необходимости `DEPLOY_PORT`). Приватный ключ или пароль **не присылать в чат, Notion или коммиты**. `DATABASE_URL` предпочтительно хранить только на VPS в защищённом файле окружения.
6. Добавить workflow приложения после переноса Rust кода, зафиксировать версии инструментов/зависимостей. На PR только испытания. Первая установка — отдельно одобряемая; после её успешной приёмки использовать только отдельные подтверждённые вручную выпуски.
7. Запустить настоящую проверку: главная/каталог/книга/чтение на **тестовых данных**, отказ неавторизованному, сохранение прогресса, перезапуск и откат на старый бинарник. Зафиксировать установленный commit SHA и URL в журнале.
8. Настроить регулярную копию PostgreSQL **на другой носитель** и проверить восстановление до появления реальных пользовательских данных/денежных операций. Схемные миграции должны быть совместимыми с версией для отката: один откат binary не откатывает БД.

## Замер 25.10.2026: ограниченный VPS, поставленный владельцем на проверку

Предоставлен вывод команд для Ubuntu 24.04.3: **1 vCPU, 961 МиБ RAM, 143 МиБ MemAvailable, swap 1,2/2,5 ГиБ занят, свободный диск 9,7 ГБ**. **Не установлено**, является ли этот уже использовавшийся хост выделенным новым VPS для tor. Ранее заявленные 4–8 ГиБ остаются ориентирами, **не фактической конфигурацией**.

**Никакого автоматического развёртывания на этот хост до проверки.** Сначала безопасно (только чтение) установить: `ps -eo pid,comm,rss,%mem,%cpu --sort=-rss | head -n 16`, `systemctl list-units --type=service --state=running --no-pager --no-legend | head -n 30`, `vmstat 1 5`, `cat /proc/pressure/memory`, `ss -lntp`. Не перезапускать хост по системному уведомлению, пока не выяснены уже работающие сервисы.

**Вариант первого визуального выпуска, если проверка выявит достаточно свободной памяти:** сборка Rust/Axum в GitHub Actions, на VPS только готовый бинарник и Nginx; `BOKARUST_DEMO_IN_MEMORY=1` с привязкой к `127.0.0.1`, явно подготовленный демонстрационный каталог (исходный `InMemoryCatalog::default()` пуст), без хранения настоящих учётных записей/денег/прогресса. Безусловный автоматический деплой запрещён до проверки памяти, реального браузера и rollback.

**Полный BookaRust:** никакого «100%» на RAM-only. Хранить данные постоянно во внешнем PostgreSQL (минимальные изменения уже готовых `Pg*` адаптеров) либо осознанно переносить адаптеры на SQLite и проверять транзакции. Не устанавливать PostgreSQL на данном хосте, пока нет ресурсного обоснования. В CI PostgreSQL остаётся допустимой одноразовой средой для тестов.

## Утилизация старого books_platform перед первым развёртыванием tor — решение владельца 25.10.2026

Проверяемый VPS `vm15714674` **не пустой**: на нём запущены 8 контейнеров прежнего NEwBOO, проект `books_platform`, конфигурация `/opt/books_platform/docker-compose.yml`. Владелец подтвердил, что старый сервис больше не используется, и разрешил убрать его. Это не означает подтверждённую очистку: SSH в рамках PR не выполнялся.

- **Состав:** `books-backend-blue`, `books-nginx`, `chapter-import-worker`, `deferred-jobs-worker`, `rulate-catalog-scanner`, `book-crawler-worker`, `trace-store`, `image-worker`.
- **Нагрузка до очистки:** около 378 МиБ RAM по сумме `docker stats`; образы 7 ГБ, из них 3,3 ГБ помечены reclaimable, три тома суммарно 48,65 МБ; 961 МиБ общей памяти и 143 МиБ `MemAvailable`. Один остановленный контейнер кроме восьми работающих пока не идентифицирован.
- **Только целевая команда удаления:** `cd /opt/books_platform && docker compose -p books_platform down --remove-orphans --volumes --rmi all`. **Она удаляет данные в томах.** `docker system prune` и удаление общей папки без предварительной проверки запрещены.
- **Проверка после:** `docker ps -a`, `docker compose ls`, `docker volume ls`, `docker system df`, `free -h`, `df -h /`, `ss -lntp`.
- **Граница:** Docker-`books-nginx` слушал `127.0.0.1:8000`, Docker image-worker — `127.0.0.1:8080`; отдельный **системный Nginx** слушает 80/443 и должен быть сохранён, пока не выяснена текущая конфигурация. SSH/Ubuntu не трогать. Внешние YDB/S3 очищаются только отдельным аудитом.
- **Следующий этап:** по фактическому объёму освободившейся памяти — либо Rust RAM-демо, либо постоянное хранилище на отдельной машине. Автодеплой до финального подтверждения очистки и безопасной настройки хоста не включать.
