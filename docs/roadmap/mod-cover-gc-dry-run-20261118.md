# MOD-COVER-OPS-01 / #667 — операторский read-only dry-run

**Статус: диагностический срез для изолированного PG18, не разрешение на удаление.** Очистка приватных обложек и публичный CDN purge (#684) независимы.

## Назначение

В репозитории есть защищённые worker-операции удаления приватных вариантов (#657), разделяемых оригиналов (#663) и проверка конкуренции двух worker (#666). Для допуска оператора до включения удаления нужна невредоносная предварительная инвентаризация.

Скрипт `tools/mod_cover_gc_dry_run.sql` выдаёт агрегированные числа по каждой причине и максимум 12 внутренних идентификаторов на группу для:

- приватных WebP-вариантов: активный слот, неполный job, отсутствие review, незрелое решение, действующая аренда, backoff, кандидат к staging/claim, признаки неконсистентности;
- разделяемых оригиналов: наличие зависимых jobs, текущего слота, ещё не удалённых вариантов и записей удаления; применимость временного порога;
- точного текущего provisional семидневного правила на базе `decided_at`/`superseded_at`, но **не** по `submitted_at`.

Вывод не содержит автора, адреса, S3 storage key, изображения, секретов или текстов решений. Внутренние IDs остаются операторскими данными; не публиковать вывод публично.

## Запуск (только разрешённая одноразовая БД)

Сначала подготовить disposable PostgreSQL 18 с актуальными SQLx миграциями и синтетическими объектами. Использовать SELECT-only роль и передать реквизиты подключения вне командной истории.

```bash
psql -X -v ON_ERROR_STOP=1 -f tools/mod_cover_gc_dry_run.sql
```

Скрипт начинает `REPEATABLE READ, READ ONLY` транзакцию, ограничивает `statement_timeout` 10 секундами и `lock_timeout` 1 секундой, затем выполняет `ROLLBACK`. Он не подключается к S3, не делает `LIST`, `DELETE`, DDL/DML или фоновых действий. При сбое или таймауте допуск не выдан.

Обозначения `eligible_to_stage`/`eligible_to_claim` — **наблюдение**, а не гарантия будущей безопасности: после снимка могут произойти модерация, публикация, новый job и смена lease. Сам worker обязан повторно проверять права и факты в транзакции.

`ANOMALY_*` — причина остановить допуск и исследовать проблему. `retain_no_jobs_legacy_or_orphan` не подтверждает отсутствие ссылок на S3; возраст или S3 LIST сами по себе не основание для удаления.

## Обязательная приёмка

1. `Repository rules` проверяет `tests/architecture/test_mod_cover_gc_readonly.py`, запрещая снятие read-only границы, DDL/DML и раскрытие ключей в примерах.
2. В Integration CI `s3-cover-build` запускает SQL на disposable PostgreSQL 18 после настоящего PostgreSQL/MinIO сценария; это проверяет синтаксис и совместимость схемы. Прогон не касается настоящих бакетов.
3. До операционного включения #667 остаются не принятыми: политика retention (семь дней в коде — не утверждённое бизнес-решение), legal hold/appeal, расписание и оператор, отдельные least-privilege credentials, обособленная инвентаризация orphan S3 с DB-absence/quarantine proof, реальные метрики и dry-run с операторским одобрением.
4. Никаких включений worker, deployment, cron, продуктивных миграций, реальных S3/CDN операций или удаления файлов данным PR не производится.

## Ограничения

Счётчики точны лишь для успешно прочитанного согласованного снимка, а примеры IDs не являются полным списком объектов. На большой БД скан может превысить таймаут — это корректный отказ, а не нулевое количество кандидатов. Инвентаризация сиротских S3-объектов данным скриптом **не реализована**.
