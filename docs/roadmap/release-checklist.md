# TOR — I-12/I-13: проверяемая приёмка выпуска

Состояние документа: 29.10.2026. Это **перечень доказательств**, не разрешение на
автоматическую выкладку. Нормативные требования: [ReleaseProfile v1](../contracts/release-profile-v1.md),
[13 задач линии I](lanes/I.md), [единая матрица 69 S](scenarios.tsv) и
[существующие карточки Notion](https://app.notion.com/p/ea10f617944046b6bf37dc8473f41c2d).

## Режимы и критерий «100%»

- **technical_beta_limited** — только включённые и проверенные функции; недоказанные
  платные действия, реклама и внешние интеграции выключены. Не означает 100%
  переноса NEwBOO.
- **full_approved_scope** — 60 действующих сценариев подтверждён по контрактам,
  все 10 REL допусков пройдены на одном конечном SHA; 9 исключений и
  замороженный URL-сборщик не считаются выполненными.
- **100% линии I** — каждый I-01… I-13 принят с кодом, протоколом испытания и
  ссылкой на подтверждённый SHA, включая защиту main, запуск на отдельном
  испытательном узле, откат и соответствие рабочему выпуску. Существование
  файла, зелёная компиляция или статусы других областей недостаточны.

## Проверка фактического CI без доступа к VPS

На **текущем SHA ветки main**, после завершения всех проверок:

```bash
export GITHUB_TOKEN="<read-only Actions token>"
SHA="$(git rev-parse HEAD)"
python3 tools/audit_release_candidate.py --sha "$SHA" --strict --out release-ci-evidence.json
python3 -m unittest discover -s tests/architecture -p 'test_release_candidate_audit.py' -v
```

`audit_release_candidate.py` читает GitHub API без записи: дополнительно
сверяет ссылку `main` **до и после** сбора результатов, ровно два зарегистрированных
автоматических workflow (`Repository rules`, `TOR integration CI`), событие `push`,
16 задач внутри общего CI (1 selector + 14 suites + `ci-required`) и задачу `rules`,
а не только зелёную оболочку после пропуска испытаний. Обнаруженные новые процессы,
отсутствующие задания, неправильный SHA, незавершённость или отмена = отказ.
Повторные запускаемые проверки берутся только по последней попытке.
Использование `--strict` даёт ненулевой код при неполном CI.

Отчёт содержит **`ci_complete`**, но неизменно
**`release_approved=false`**: внешние выплаты, реальные S3/ключи, состояние
стенда, защита GitHub и паритет 61 сценария требуют отдельной приёмки.
Токен в отчёт не записывается. Скрипт не подключается к SSH, не меняет
рабочий VPS и не заменяет действующую ручную кнопку выпуска.


## I-06: проверка действующего ruleset до SSH (31.10.2026)

`main.protected=true` в `branches/main` само по себе недостаточно. TOR использует
активный GitHub [ruleset main #26235453](https://github.com/calex794/tor/rules/26235453);
классическая branch protection может одновременно возвращать
`protection.enabled=false`. `tools/check_one_click_release_ci.py` принимает
не *флаг*, а проверяемые активные **effective branch rules** на exact `main`.
Нужны обязательный PR, запрет force-push/deletion и **оба** GitHub Actions
контекста `rules` и `ci-required` с проверенным provider ID. Parent
organization rulesets учитываются. Сбой чтения, неверный источник, неполный
список, смена SHA или settings → немедленный отказ.

GitHub не всегда возвращает поле `bypass_actors` на токенах только для чтения.
Поэтому действующий ruleset без этого поля принимается **только с
предварительно проверенным id и updated_at**. Любое редактирование правил
блокирует выпуск до администраторской повторной проверки и обновления pin.
Это не означает, что GitHub предоставляет через read-only API независимое
доказательство отсутствия всех возможных bypass-акторов.

Без установки/SSH, на **точном текущем SHA main**, оператор может проверить
только политику (из безопасного окружения с GitHub read token):

```bash
export GITHUB_TOKEN="<GitHub token with metadata read>"
SHA="$(git ls-remote origin refs/heads/main | cut -f1)"
python3 tools/check_one_click_release_ci.py \
  --repo calex794/tor --sha "$SHA" --policy-only
```

Обычный запуск **дополнительно** требует весь `audit_release_candidate.collect()`
с успешными 14 suites, `ci-required` и `rules`, с повторной
проверкой ruleset и exact `main` непосредственно перед разрешением сборки.
Сам по себе успешный preflight **не** даёт разрешения на выкладку: staging,
SQLx downgrade/rollback safety, backup/restore и внешний payment gate
проверяются отдельно. См. [I-06/P0 #321](https://github.com/calex794/tor/issues/321).

Таблица описывает **работы и доказательства**, а не 13 выполненных пунктов.
Для статусной приёмки нужна конкретная запись `задача → SHA → реальный CI/HTTP/PG/браузер → отказ → статус`.
Часть прежних путей в старом плане переименована: `deploy/release.sh`
не используется, действующий механизм — `ops/one-click-release-vps.sh`.
Не создавать вторую таблицу 69 сценариев.

## REL-01…REL-10: границы автоматической проверки

| Допуск | Что обязательно доказать | Что не следует выводить из CI |
| --- | --- | --- |
| REL-01 | Rust fmt/Clippy/unit/build на одном SHA | Что приложение успешно обслуживает посетителей |
| REL-02 | Дорожная карта, границы модулей, контракты, маршруты | Что 61 пользовательский сценарий выполнен |
| REL-03 | Fresh/upgrade PG18, уникальность, восстановление БД | Совместимость со всеми рабочими данными |
| REL-04 | Приватный S3, анонимный отказ, WebCrypto, KEK, V1 | Наличие рабочих ключей и настроек реального S3 |
| REL-05 | Права автора/читателя, V1/V2, отказ/возврат/блокировка | Что все платные страницы уже доступны публично |
| REL-06 | Денежная книга, начисления, выплаты, возвраты, реклама | Что внутренний тестовый кошелёк равен настоящим деньгам |
| REL-07 | Рекомендации, согласия, сигналы RIL, приватность | Что качество персонализации измерено на аудитории |
| REL-08 | Память/CPU, перезапуск служб, аварии PG/S3, резервные копии | Что одни лишь локальные испытания означают стабильность VPS |
| REL-09 | Настоящий Chromium, PG/S3, мобильный вид, отрицательные пути | Что демонстрационный сайт полностью соответствует NEwBOO |
| REL-10 | HTTPS, /readyz, текущий установленный SHA, откат и наблюдение | Что успешная публикация PR обновила рабочий сайт |

**Фактические блокеры на момент составления:**

- Готовность основного кода **не равна** утверждённому `full_approved_scope`.
  Прямой платёжный источник и выплаты, часть социального функционала,
  импорт и персональные рекомендации пока не доказаны. Флаги по умолчанию выключены.
- **I-06 не пройден.** [GitHub branches/main](https://api.github.com/repos/calex794/tor/branches/main)
  29.10 вернул `protected=false`, `protection.enabled=false` и
  `required_status_checks.enforcement_level=off`; [rulesets](https://api.github.com/repos/calex794/tor/rulesets)
  вернул `[]`. Это **подтверждённое отсутствие** обязательной защиты.
  `tools/check_one_click_release_ci.py` теперь отказывает **до SSH**, когда
  `main` не защищена, проверка `rules` из GitHub Actions не обязательна
  или администратор может обойти правило. Защита повторно проверяется
  после завершения CI — нельзя снимать её посреди запуска.
  До ручной настройки в GitHub Settings одношаговый выпуск намеренно
  заблокирован. Код не меняет правила GitHub самостоятельно.
  В настройках репозитория следует потребовать PR, проверку `rules`,
  применение ограничений к администраторам и запрет force-push/удаления;
  отдельно подтвердить запрет прямой записи тестовым действием.
  **Проверка `branches/main` доказывает только обязательность статуса,
  но не настройку PR-процесса и остальных ограничений.**
- Для хранилища трасс [OBS-10](https://github.com/calex794/tor/pull/183)
  прошёл процессный тест 5/5 и 15/15 GitHub Actions до слияния. Но отдельный
  systemd-стенд и ограничение памяти около 1 ГиБ не испытаны, а
  `tor-trace-store` не входит в обычный подписанный пакет выпуска.
- Состояние VPS нельзя узнавать по состоянию `main`: установленный
  SHA, свежая резервная копия **вне** VPS и фактический возврат после сбоя
  требуют отдельного подтверждения.

## Протокол финального допуска

1. Зафиксировать точный `main` SHA; получить проверенный CI-отчёт по этому SHA.
2. Проверить только включённые возможности и безопасное выключение остальных
   по [списку выпускных флагов](../contracts/release-flags-v1.json).
3. На **изолированном** испытательном узле подтвердить PostgreSQL, S3,
   HTTPS, восстановление копии, перезапуск службы, память/диск и откат.
4. Сверить 61 действующий S с [канонической матрицей Notion](https://app.notion.com/p/ea10f617944046b6bf37dc8473f41c2d);
   записать точный SHA, действительный браузерный/PG/HTTP опыт либо блокер.
5. Только после отдельных допусков A–H, I и REL-01…10 принять решение о
   `technical_beta_limited` или `full_approved_scope`. Не включать
   платные, рекламные или экспериментальные компоненты при недоказанных правах.

**Ограничение:** этот документ и новая программа не запускают публикацию сайта,
не изменяют существующий `tor-one-click-release.yml` и не дают автоматического
разрешения на деньги или открытие индексации.
