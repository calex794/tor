# TOR / MOD-WORKBENCH-01 — единый кабинет модератора

**Продуктовое решение 2026-11-06. Статус: контракт принят как новая постановка; реализация не завершена.**  
Роли: модератор **сайта** или администратор. Член команды книги с ролью `moderator` **не получает** доступ к этому кабинету.  
Это дополняет [A-05](a05-book-registration-approval-only.md), не возвращает MOD-C01/C02/C03: отдельные главы **не** требуют модераторского одобрения.

## Маршруты и три очереди

Один приватный кабинет `/moderation/books`, серверные вкладки (не «фейковые» клиентские фильтры):
- **Регистрация** — `/moderation/books?tab=registration`: книги, ожидающие решения по регистрации.
- **Обложки** — `/moderation/books?tab=covers`: первоначальные и новые версии обложек, ожидающие решения.
- **Удаление** — `/moderation/books?tab=deletion`: запросы владельцев на обычное удаление.

Счётчики только по действительно ожидающим заявкам, выдаются после действующей сессии и site-role; keyset pagination `(created_at,id)`, максимум 40 строк, фильтры `pending/reviewed`, поиск по идентификатору и названию. Для каждой карточки: книга, владелец, время подачи, тип запроса, защищённый предпросмотр, ревизия, история, действия «Одобрить»/«Отклонить» (для отказа причина обязательна). Отдельный режим «История» — фильтр, а не четвёртый тип очереди. Выбор записи, курсор и количество не раскрывают приватную информацию неавторизованным пользователям.

**Критично:** существующие кнопки удержания и смены видимости являются экстренными административными операциями; оставить их в отдельном подразделе «Контроль», а не считать решением по новой заявке. `admin_hold`, `visibility_status`, `visibility` и `lifecycle_status` — разные состояния.

## 1. Регистрация книги

`create_owned_book` создаёт `books.visibility='draft'` и `visibility_status='pending_moderation'`. Модератор рассматривает заявку и проверяет сведения книги, дубли, право на контент и ограничения.

- `approve`: в **одной** транзакции подтверждает текущую заявку/ревизию, назначает `visibility_status='active'`, создаёт append-only решение `registration/approved`, связывает книгу с этим решением. Авторская `visibility=draft/public` не меняется за модератора.
- `reject`: записывает решение, обязательную причину и безопасный непубличный статус (политика для исправления/повторной подачи), не теряя историю. Книга не должна попадать в каталог.
- Дальнейшее `hidden/blocked` не стирает, **кто первоначально одобрил регистрацию**; это отдельное последующее действие.
- Анонимная карточка, поиск, рекомендации, клиентский JSON, SEO, push и публичные события **не получают** reviewer ID, display name или внутренний журнал.

## 2. Первичная обложка и замена

**Всё**, включая первую обложку при создании книги, проверяется человеком *до* того, как её можно выдать в публичном HTML, `/covers/...` или CDN/S3.

Разделить G и B:
1. Owner/member с разрешением на загрузку передаёт изображение в **приватный** staging; G проверяет MIME+magic, 8MiB/24MP, декодирование, EXIF/анимацию, делает immutable main/card WebP и hashes. Это только `processed`, **не** `approved`.
2. B создаёт `cover_review_requests` на конкретный `cover_variant_jobs.id` + исходные SHA-256 и `expected_slot_revision`, статус `pending`. Для одной книги допускается один актуальный ожидающий кандидат; устаревшая заявка помечается `superseded` с историей.
3. Модератор через защищённый предпросмотр видит технически обработанное изображение. Публичные URL и ключи S3, сырые исходники, SVG/HTML, произвольные внешние URL и скрипты на страницу не попадают.
4. `approve`: в одной B-транзакции проверяет действующую site-role, live session, точную ревизию заявки, immutable hash, Book owner/hold/lifecycle и ожидаемую ревизию слота; записывает `cover/approved` и **только затем** обновляет `book_cover_slots`. G worker **не** прикрепляет обработанный файл автоматически. Существующий `attach_ready_job` нельзя выполнять позднее по истёкшему worker lease: review создаёт отдельное право на attach, не заимствует `locked_until` из G.
5. `reject`: причина обязательна, старый публичный слот сохраняется; при первой обложке остаётся штатный нейтральный placeholder. Staging и CDN-копии после решения/TTL очищаются отдельно, без влияния на историю решений.
6. Подтверждение **старой** заявки после новой загрузки/смены владельца/hold/удаления возвращает 409, без переключения слота. Прямой S3/CDN grant обязан проверять **одобренный текущий слот**, а не просто статус G job `done`.

Одобрение регистрации книги **не является** одобрением обложки. Регистрация может быть принята без обложки; до одобрения первичной картинки показывается нейтральная заглушка. Это предположение для MVP, которое нельзя превращать в блокировку регистрации без отдельного решения.

## 3. Запрос на обычное удаление книги — P0 BR-060/#570

Текущий `#589` допускает owner `start → pending_deletion → complete → ordinary_deleted` по двум проверкам пароля. **Это несоответствие новому требованию.**
- Владелец подтверждает пароль/step-up один раз при `request deletion`, сервер блокирует active owner/session/book, записывает запрос, исходный жизненный цикл и ревизию; книга переводится в `pending_deletion` согласно текущим правилам public discovery/direct view.
- У владельца в этом состоянии **нет** полномочия `complete`, даже при повторном пароле. Переход `pending_deletion → ordinary_deleted` возможен **только** в серверной транзакции решения site moderator/admin по ожидающей заявке с явным `approve`.
- `reject`: причина, уведомление владельцу, восстановление предшествующего жизненного цикла и видимости при соблюдении CAS (или `stale`, без слепого отката чужих изменений). Системная история запросов остаётся.
- Сохранить уже принятые контракт BR-060: купленная immutable V1, закреплённая бесплатная V1, позиции чтения, приватная библиотека «Удалена» после **одобренного** обычного удаления; hard/legal/admin block и refund/age revoke продолжают ограничивать фактическое чтение. Физический DELETE не происходит.
- Рекомендуется запретить модератору одобрять **собственную** книгу; возможный site-admin override должен быть явным и аудируемым.
- API `complete` владельца и его HTTP-кнопка должны быть удалены/заблокированы **вместе с** переписыванием текущих PG/HTTP/MinIO тестов. Закрыть путь только на фронтенде недостаточно.

## Системное «кто одобрил» — не публичное поле

Не путать: регистрация книги, утверждение новой версии обложки и согласование удаления могут иметь **разных** модераторов.

Хранить в append-only `moderation_decisions` со ссылкой на `moderation_requests` (`id, book_id, kind, submitted_by, submitted_at, subject_revision, status, details`) и полями `reviewer_user_id, decided_at, outcome, reason, expected_revision`. В книге/закрытой materialized projection держать ссылку на **последнее утверждающее решение регистрации**, в слоте — на **утверждение конкретной обложки**, в заявке удаления — на решение об удалении. Reviewer ID неизменяем и проверяется внешним ключом; отображаемое имя на момент просмотра может изменяться.

`GET /moderation/books/{id}/history` (или отдельный site-role-only запрос) даёт хронологию, заявку, исходную/новую ревизию, модератора и время. Автор получает только статус и обезличенную причину отказа. Никаких reviewer полей в публичных карточках, публичных `/books/{id}`, TOC, recommendations, CDN metadata, поисковом индексе или social preview.

В каждой approve/reject транзакции: блокировка live session + site-role, Book/subject row FOR UPDATE, CAS expected_revision, проверка одного terminal decision на запрос, запись audit **в том же commit**. Повторные одинаковые решения не дублируют события; параллельные конкурирующие — 409.

## Этапы реализации (без двойного функционала)

1. **P0 safety / deletion**: ввод одобрения удаления модератором, отказ владельцу в complete, миграция новых request/decision state и корректировка BR-060 тестов. Сначала закрыть обход прямым API.
2. **Registration**: выделить утверждение регистрации из произвольной смены `visibility_status`, сохранить reviewer attribution и историю; адаптировать существующую A-05 queue.
3. **Covers**: отделить G `processed` от B `approved`, заменить автоматическое `attach_ready_job`, безопасная очередь initial/replacement, атомарные slot + decision + CDN visibility.
4. **Unified UI**: три серверные вкладки со счётчиками и реальными запросами к заявкам, действиями, историями и фильтрами; экстренный hold/visibility отдельным подразделом.
5. **Acceptance**: HTTP/PG/MinIO/Chromium на 390/1440; автор без site-role не видит reviewer identity; сайд-роль книжного модератора не даёт site permissions; кража CSRF/смена статуса/ревизии и self-approval запрещены; первая/сменная cover не публична до approve, rejected replacement не сбивает предыдущую; после отказа удаления public state возвращается; после approve BR-060 private archive/read+paid V1 сохраняются.

## Проверяемые негативные случаи

- Owner дважды подтверждает удаление, но **нет** решения модерации → `ordinary_deleted` невозможен.
- Модератор книги/переводчик/обычный reader, отозванная роль или сессия → approve/reject 403/401.
- Два модератора одновременно решают одну заявку → ровно одно terminal decision, проигравший 409.
- Смена cover job или slot во время review → старое одобрение не публикует старую картинку.
- Неодобренная первичная обложка никогда не появляется на публичном URL; при замене старая одобренная остаётся.
- Скрытие reviewer name в HTML при открытом REST endpoint не считается защитой: server query и роли проверяются до формирования ответа.
- Возврат/отклонение удаления не удаляет paid facts, saved free pins и курсор.

## Известные ограничения и согласование

- Текущая TOR регистрация уже создаёт `pending_moderation` и `moderation_book_visibility_events`, но не хранит независимую registration approval identity.
- G `cover_variant_jobs` + B `book_cover_slots` сейчас автоматически прикрепляют готовый job: **реальный bypass cover review**; флаг отключённого worker не является доказательством безопасного включения.
- `book_ordinary_deletion.rs` позволяет owner `complete`: **реальный bypass deletion review**.
- Existing accepted PR/CI for BR-060 must be kept as retention/access evidence, not proof of moderator approval. S025 cover delivery feature flags stay OFF until review gates and full acceptance.
- Не разворачивать production/VPS и не накатывать миграции на постоянную БД без отдельной команды.
