## Цель, границы, утверждённые определения

**Продукт:** повысить количество содержательных открытий других собственных новелл TOR и их экономический вклад, не ухудшая чтение исходной книги. Нельзя объявлять CTR, рендер карточки или простой переход приростом выручки без надёжного эксперимента.

1. **Одна Book = самостоятельная новелла.** Для томов/серий нет отдельной обязательной модели, штрафа, квоты и этапа. Разные Book одного владельца разрешено рекомендовать одновременно; одну Book повторять нельзя. Ручные связи между самостоятельными произведениями сохраняются как необязательный источник кандидатов.
2. **«Автор» в распределении = текущий владелец исходной Book (`books.owner_user_id`), не оригинальный писатель или переводчик.** Источник `author` — *другие* доступные Book с тем же владельцем. `teammate` — доступные Book другого владельца, принадлежащего к официально активной, подтверждённой команде исходной Book. `site` — остальные доступные Book других владельцев вне этой команды. При пересечении источник назначается один раз: автор → команда → сайт.
3. **Контекст вместо поведенческого профиля:** жанры, теги, язык, разрешённые вручную связи и *явные* оценки/исключения читателя. Старые индивидуальные REC/FLOW producers, история переходов/показов, идентификационные tickets и согласия на прежний сбор не возвращаются; текущие CAS и «Не интересно» сохраняются.
4. **Обязательный допуск:** статус публикации, права конкретного зрителя и возраст, admin hold, pending deletion/deletion, текущие ограничения и собственное скрытие применяются до выдачи и для fallback. Никаких платных/private/admin страниц в органической полке после бесплатной главы; провал необязательных рекомендаций не ломает чтение.
5. **Единственное место после текста и навигации бесплатной главы:** целевой вид — пять разных Book (минимум четыре, **если** есть минимум четыре разрешённых кандидата в действующих категориях). Редакционная кампания и органика размещаются внутри **одной** полки, а не отдельными конкурирующими блоками. Редакция может занимать до четырёх из пяти мест; остальное — органические рекомендации. Это цель открытого #857, не факт текущего `main`.
6. **Проценты — цели по множеству показов органических слотов**, а не целочисленное обещание внутри каждой полки из пяти мест. Редакционные места, наблюдаемые показы, клики, подтверждённое чтение и покупки измеряются независимо.

### Настраиваемая политика долей — продуктовое решение от 13.11.2026

| Параметр | Значение по умолчанию | Редактируемость |
| --- | ---: | --- |
| Обычный режим: `author` | 50% | администратор |
| Обычный режим: `teammate` | 40% | администратор |
| Обычный режим: `site` | 10% | администратор |
| Без доступных командных книг: `author` | 70% | администратор |
| Без доступных командных книг: `teammate` | 0% (не редактируется в этом режиме) | фиксировано |
| Без доступных командных книг: `site` | 30% | администратор |

**Инварианты:** обычная тройка = 100%; пара «без команды» = 100%. Только целые числа 0…100, проверка на сервере и в PostgreSQL. Два набора значений независимы: нельзя автоматически пересчитывать 50/40/10 в 83/17 вместо согласованного 70/30. Наличие команды определяется наличием **доступных кандидатов** `teammate` после проверки прав, а не только записью о составе команды. Редакционные слоты распределяются по *другой* политике и не участвуют в этих процентах.

**Недостаток кандидатов:** в обоих режимах ни нулевой инвентарь, ни явно установленная нулевая квота не порождают фиктивную Book. Если категория с положительной квотой пуста, распределять её незанятые места между оставшимися ненулевыми категориями детерминированно. При пустой команде в первую очередь применяется особая утверждённая пара 70/30 (или её текущая настройка), а не обычная пропорция. Если остаётся один разрешённый источник — он занимает все доступные места. Если все разрешённые источники пусты — полка неполная/пустая с диагностикой, но без запрещённых замен. Явный административный 0% **запрещает** категорию и не отменяется автоматическим fallback. Новую общую схему поведения при отсутствующем владельце/сайте проверить против существующего `weights_for_availability`; никаких тихих изменений действующего кода без отдельной приёмки.

**Ограничение одного владельца:** если все Book сайта принадлежат одному `owner_user_id`, `site` для исходной Book естественным образом пуст. Панель обязана показывать фактическую доступность источников и эффективную долю/перенос неиспользованной квоты; не переименовывать книги владельца в «сайт» для красивой статистики.

## REC-ADMIN-01 — единая административная панель (новое обязательное требование)

**Единственный вход:** `GET /admin/recommendations` (новый проектируемый маршрут, **сейчас отсутствует**). Объединить навигацию существующих `/me/recommendations/contextual`, `/me/recommendations/shelf-preview`, `/admin/promotion/editorial` и `/admin/audience/exposure`, не копируя их базы/обработчики и не открывая доступ посторонним. Области панели:

1. **Обзор:** текущее состояние REC flag и контекстного поколения, валидные источники, размер доступного инвентаря и ограничение целевой полки; флаги OFF — честно показаны.
2. **Доли органики:** пять числовых полей для `author/team/site` и `author/site` без команды; серверный расчёт сумм 100%, явная подпись «проценты по множеству выдач, не по одной главе»; кнопки «Предпросмотр», «Сохранить», «Восстановить значения по умолчанию».
3. **Предпросмотр:** выбор исходной Book и бесплатной главы; для допустимой гостевой и тестовой возрастной роли показать состав из 4–5 разных Book, категории, реальные доступные/нулевые пулы и *целевые против фактических* квоты, число занятых редакцией слотов. Не создавать FLOW proofs и не записывать показы.
4. **Редакционные назначения:** текущее состояние и переход к существующему управлению; видимое объяснение, что редакционный лимит — отдельная настройка, а 50/40/10 касается только оставшихся органических мест. Изменение источника показа не считается платным списанием.
5. **Алгоритм и аналитика:** текущая версия scoring/generation, hold/rollback, понятные причины выдачи, ссылки на сводки `surface × source`, измерение качества и отсутствие индивидуальной атрибуции; позже вкладка эксперимента.
6. **История и откат:** revision, кто/когда/какие доли изменил, атомарный возврат к предыдущему валидному набору через новую CAS-ревизию, неизменяемый аудит; старые активные суммы не переинтерпретируются задним числом.

**Модель хранения (к проектированию/реализации в шаге 04):** одна F-owned PostgreSQL policy для всего сайта, положительная монотонная `revision`, 5 integer `*_pct`, метаданные актёра и времени; отдельный ограниченный append-only журнал смен политики. Нужна additive миграция с новым непересекающимся случайным номером (не выкатывать на VPS в рамках плана), FK/role boundaries, CHECK диапазона и суммы, транзакционный CAS `expected_revision`. Любая смена вступает в силу на новых выдачах, не переписывает исторические показания; явно определённая cache invalidation / policy version. Никаких новых внешних платёжных или analytics таблиц.

**Безопасность и UX:** только текущий действующий администратор по A, fresh role/session на каждом GET и POST, CSRF/Origin/actor, POST без возможности случайного повторного применения, `409` на устаревшую revision, `422` на сумму ≠100/ошибочное число, `401/403` без права. Нативные HTML-формы без JavaScript, доступность и 390/1440 без горизонтального переполнения. Не включать `TOR_RECOMMENDATIONS_ENABLED` автоматически при сохранении процентов.

**Приёмка:** значения по умолчанию 50/40/10 и 70/30, успешная смена в 40/30/30 и 60/40, защита от 50/40/20 и отрицательных/нечисловых значений, два одновременных администратора, недействующая роль, CSRF/Origin, restart persistence, old policy preview, отсутствие FLOW записей при предпросмотре; PG-распределение 100 ротаций и выборка каталога 1000 Book, случаи «все Book одного владельца», пустая команда, пустой автор, сайт без кандидатов, нулевая пользовательская квота, скрытая/удаляемая/18+/21+ книга, editorial+organic без дублей, 4–5 при достаточном подходящем инвентаре. Все тесты на конечном PR SHA с post-merge на main; только после этого статус «принято».

## Технические границы и доказательства

- **F** владеет алгоритмом, pool-предикатом и настройкой; **H** SSR/формы; **A** авторизацией через существующие проверки; **I** маршрутами, миграцией, RIL и интеграционными тестами; **FLOW** учётом наблюдений; **D** исключительно авторитетными агрегатами денег. Никакого дублирования бизнес-логики в web.
- Измеряемые сигналы: зарегистрированная карточка ≠ подтверждённый DOM ≠ 60% видимость не менее секунды ≠ клик ≠ подтверждённое начало/завершение главы ≠ покупка. Нет отождествления этих фактов, не выводить коэффициенты, если знаменатель неполон; не хранить actor trail для поиска рекламных «конверсий».
- Два независимых переключателя: существующая органика `TOR_RECOMMENDATIONS_ENABLED` и действующий режим редакционных назначений. Административная настройка долей **не** меняет ни один переключатель, не создаёт выдачу из неразрешённой Book и не добавляет рекламный billable fact.
- Исторические REC-02/03 behavioral, индивидуальная REC-13 атрибуция, связанные выдачи томов и платные S042/S043 не становятся новой активной очередью только из-за старых документов. Старый `#829` superseded принятым `#845`.
- Каждый кодовый этап — отдельный небольшой PR: от актуального `main`, обязательные отрицательные проверки, PostgreSQL/HTTP/Chromium (для UI), `Repository rules`, `Integration CI`, `REC acceptance` где применимо, просмотр артефактов, затем squash и post-merge. **Ни деплоя, ни боевых миграций по этому плану без отдельного разрешения**.
