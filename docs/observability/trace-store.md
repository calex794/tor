# OBS-03 — независимое хранение технических трасс TOR

**Состояние:** отдельная служба Rust + SQLite, выключена по умолчанию. Она не заменяет RIL, PostgreSQL и систему безопасности. Для первых проверок запускается на выделенной испытательной машине. Старые настройки и данные NEwBOO автоматически не копируются.

## Пользовательский сценарий оператора

1. В приложении появляется ошибка или медленный запрос. HTTP-ответ содержит созданный сервером `x-request-id`. Лог RIL/метрики позволяют узнать семейство маршрута.
2. Закончившийся HTTP-запрос вместе с ограниченными числовыми SQLx-операциями целиком попадает в выборку или пропускается целиком. При включённом отдельном процессе запись выполняется через очередь, **не задерживая ответ клиенту**.
3. Оператор смотрит архив командой `tor-trace-store report /var/lib/tor-traces/traces.sqlite3 50`. Команда сообщает **сколько всего записей сохранено, сколько совпало и сколько реально показано**. Это не поиск по «последним ста» под видом полного архива.
4. Служба удаляет записи старше трёх дней, хранит не более 50 000 корневых трасс и ограничивает SQLite основным файлом до 64 МиБ. Заполнение диска или отсутствие процесса не должно останавливать чтение и покупку книг.

## Изоляция и данные

- Соединение **только через закрытый Unix-сокет** с правом `0600` и каталогами `0700`. Нет TCP, публичного API, пути поиска по чужим аккаунтам или личных идентификаторов.
- Протокол `OBS1` — только заранее заданные числа: `trace_id`, одна из пяти групп маршрута, одна из пяти групп статуса, длительность, наличие SQLx, счётчик, время и максимум 8 дочерних измерений.
- Нет текста SQL, аргументов запросов, IP, имени пользователя, cookie, полного URL, referer и user-agent.
- SQLite — единственный процесс записи; таблица корней и отдельная таблица дочерних измерений, связанная внешним ключом с каскадным удалением.
- Техническое время SQLx включает сетевые операции и обработку ответа: это **не** показание времени исполнения SQL сервером PostgreSQL.
- При сбое хранилища заявляется потеря диагностических данных. Счётчики `tor_trace_export_failed_total` и `tor_trace_export_dropped_total` позволяют увидеть её. Секреты и входные данные не выводятся в журналы ошибок.
- Данные, ранее чем TTL, могут находиться в свободных страницах SQLite до физической очистки файла; `secure_delete=ON` снижает риск остаточного чтения. Журнал отката может временно увеличить общий расход диска сверх ограничения основного файла.

## Установка на отдельном испытательном сервере

1. Собрать бинарный файл `cargo build --release -p tor-observability --bin tor-trace-store` вместе с сервером `tor-web`.
2. Установить `ops/tor-trace-store.service.example` как отдельную службу **только на изолированном узле**; не активировать автоматически. В действующем образце web использует `tor-deploy`, поэтому writer должен иметь того же владельца приватного сокета (`User=tor-deploy`, `Group=tor-deploy`). Перед любой установкой сверить фактические права `systemctl show tor-web.service -p User -p Group`.
3. После проверки владельцев, прав и доступного диска запустить сервис. Для `tor-web` под тем же пользователем задать `TOR_TRACE_STORE_SOCKET=/run/tor-traces/traces.sock` и перезапустить сайт.
4. На испытательном сайте создать несколько обычных и ошибочных запросов, убедиться в росте `tor_trace_export_sent_total`, проверить `report`, затем перезапустить писатель и повторить чтение архива.
5. При выключении службы или переполнении очереди сайт должен продолжать отвечать; у экспортёра должны расти счётчики потерь, а в архив не должны попадать данные пользователей.

**Блокирующее условие для VPS (проверено по коду):** стандартная кнопка обновления в `tor-one-click-release.yml` собирает и подписывает только `tor-web` и `tor-migrate`. `tor-trace-store` **не включён** в подписанный выпуск; пример `ExecStart=/opt/tor/current/tor-trace-store` не заработает на обычном выпуске. Не запускать службу на рабочем VPS до отдельной задачи безопасной доставки и обновления root-owned бинарника. Простое изменение GitHub-процедуры не обновляет установленный однажды привилегированный обработчик `/usr/local/sbin/tor-one-click-release`.

**Не выставлять** `TOR_TRACE_STORE_SOCKET` в среде рабочего сайта до проверки службы и разрешений. Изменения настроек сервера и выпуск требуют отдельного подтверждённого шага.

## Приёмка и ограничения первого участка

`cargo test -p tor-observability --all-targets`, `cargo test -p tor-web --all-targets`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`. Отдельный тест должен поднять настоящий процесс с Unix-сокетом, проверить повреждённый пакет и сохранение в SQLite. После перезапуска поиск старой трассы должен работать; TTL и ограничение количества удаляют и дочерние измерения.

Не готово: графическая страница администратора, агрегирование по нескольким серверам, доказательство развёртывания на VPS и автоматическая проверка пределов диска с учётом временного журнала.


## OBS-04 — защищённая страница поиска по идентификатору запроса

После запуска отдельной службы хранения оператор открывает `https://<испытательный-хост>/ops/traces`, вводит имя **operator** и специальный пароль из переменной `TOR_OBS_OPERATOR_PASSWORD`. Пароль должен состоять из **32–256 печатных символов ASCII**. Пример значения в документации не приводится; генерируйте секрет вне GitHub и храните его в файле окружения службы с закрытыми правами. Запрещается пересылать Basic-пароль по открытому HTTP; основной TOR слушает только локальный адрес за проверенным HTTPS-посредником.

Пароль не является обычной учётной записью сайта: в TOR пока нет проверенной системы ролей сотрудников. Права администратора по cookie или произвольному `user_id` не выдаются. Отсутствующий или неверный пароль приводит к HTTP **401** без чтения трассы. Проверка существует независимо от состояния хранилища.

После входа оператор вставляет 32-значный `x-request-id` из HTTP-ответа. Страница показывает длительность запроса, группу маршрута, группу статуса, числовые дочерние SQLx-операции и возможные признаки замедления. Она не показывает SQL-текст, IP-адрес, заголовки запроса, cookie и ID пользователя. Система не утверждает, что время SQLx равно времени исполнения запроса на сервере PostgreSQL.

- **200** — запись найдена в SQLite, доступны сохранённые измерения.
- **400** — идентификатор неверен; не отображаются сырые данные запроса.
- **404** — совпадений нет в **сохранённом архиве**. Это не означает, что HTTP-запроса не было: он мог не попасть в выборку, выйти за 3-дневный срок или не быть доставлен.
- **503** — служба не включена или сокет недоступен; не подменять это сообщением «запрос не найден».
- Каждая выдача содержит `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, запрет встраивания и ограничение выполнения сценариев в браузере.

Веб-сервер не открывает файл SQLite. Протокол поиска `OBQ1/OBR1` передаёт только идентификатор и ограниченный ответ через закрытый Unix-сокет отдельного процесса. Основные запросы сайта не зависят от работы страницы; поиск выполняется отдельно с ограничением времени.

**Проверки перед установкой на VPS:** отказ без пароля/при неверном пароле, попытка подменить Basic-заголовок, отсеивание некорректного `id`, реальный поиск через Unix-сокет, повреждённый ответ, отсутствие хранилища, сохранение закрытых заголовков. При действующей авторизации ещё требуются испытания в настоящем браузере на испытательном HTTPS-сервере. Не считать обычные учётные записи администраторскими.


## OBS-05 — служебная сводка сайта (без нового сборщика данных)

Добавлена закрытая страница `GET /ops/overview` с той же **отдельной** проверкой `TOR_OBS_OPERATOR_PASSWORD` и HTTP Basic `operator`, что и `/ops/traces`. Обычная учётная запись пользователя, cookie или секрет для `/metrics` не разрешают доступ. При отсутствии корректного пароля возвращается **401 до любых обращений к PostgreSQL и /proc**. Ответ не кешируется, не индексируется, не встраивается, запрещает внешние сценарии.

Панели показывают только реальные агрегаты:
- **PostgreSQL:** проверка `PgCatalog::probe()` со сроком 950 мс. «Нет подключения» в демонстрационном режиме и «недоступно» при ошибке — два разных статуса. Это не гарантирует отсутствие проблем в других таблицах или внешних службах.
- **Память и процессор:** Linux `/proc/self/status` (VmRSS) и `/proc/self/schedstat` (накопленное время исполнения на CPU). Доля CPU берётся **между двумя просмотрами**, относительно одного ядра; на первом просмотре или на неподдерживаемой системе показано «Нет измерения». Это **не** общая загрузка сервера.
- **HTTP:** существующий `HttpMetrics`, завершённые запросы, ответы 4xx/5xx и запросы более одной секунды. Счётчики локальные, обнуляются при перезапуске. HTTP 4xx не обязательно означает сбой.
- **RIL:** число зарегистрированных методов и версия классификатора, уже существующие атомарные счётчики потерянных технических событий. RIL не заменяет права доступа.
- **Фоновые задачи:** только агрегаты статусов незавершённых и безвозвратно ошибочных партий `ril_flush_batches` и `cover_variant_jobs`. SQL находится **в собственных репозиториях** функциональных пакетов, результат — только числа. Одни статусы не доказывают наличие живых фоновых исполнителей.
- **Доставка трасс:** путь Unix-сокета настроен или нет; при наличии — подтверждённые, ошибочные и отброшенные сообщения существующего неблокирующего издателя. Наличие пути не гарантирует доступность отдельного процесса SQLite.

Для каждой проверки PostgreSQL действует отдельное ограничение времени. При отказе одной очереди или отсутствии `/proc` страница доступна, но явно выводит «Нет измерения» вместо выдуманного нуля. Не включать статус «всё работает» только на основании открытия страницы.

**Проверка:** `cargo test -p tor-observability`, `cargo test -p tor-web`, реальные `tor_app` тесты очередей PostgreSQL, `cargo clippy --workspace --all-targets -- -D warnings`, `python3 tools/check_ril_governance.py`, браузерные испытания `tools/operator_trace_visual_smoke.cjs` на настольной и мобильной ширине. Скриншоты сохраняются вместе с испытаниями трасс.

**Эксплуатационный статус:** страница выключена по умолчанию, пока не задан сильный отдельный секрет; запуск SQLite-процесса, HTTPS, работоспособность фоновых исполнителей и установка на рабочий VPS остаются независимыми проверками.


## OBS-06 — обнаружение остановленных фоновых циклов и проблем очередей

Дополнение к `GET /ops/overview`. Только чтение и диагностика, без автоматического изменения статусов заданий, повторного выполнения или принудительного сброса аренды.

**Сборщик RIL** работает в данном процессе сайта каждые 10 секунд и теперь сохраняет ограниченное состояние собственных циклов в памяти: начало наблюдения, число завершённых циклов, число неудачных, количество ошибок подряд, момент последнего завершения и признак выполняющегося цикла. Данные не содержат идентификаторов пользователей, SQL, URL или ID партий. Сбой постановки, получения, материализации, барьера очереди либо очистки помечает цикл неудачным, но **не останавливает HTTP-запросы**. Повторяется то же сохранённое задание/идентификатор, как ранее.

- Нет законченного цикла **90 секунд** после создания сборщика, после предыдущего цикла или при текущем зависшем цикле — предупреждение «возможная остановка/зависание».
- **Три подряд** цикла с неудачами — предупреждение о повторяющихся технических ошибках, даже если завершённость очереди пока не известна.
- После успешного цикла последовательный счётчик ошибок обнуляется; общее число ошибочных циклов остаётся с запуска процесса.
- Монитор RIL относится **только к данному процессу**. Другие процессы, отдельный сервер или прошлые перезапуски он не подтверждает. В демонстрационном режиме сборщик не запускается, что обозначено явно.

**RIL/обложки: агрегаты из существующей PostgreSQL**, с ролью `tor_app` и ограничением времени чтения. Без новых таблиц, миграций, ID пользователей и SQL в HTTP:
- Подлежащие обработке задания, созданные **более 5 минут** назад, с `run_after <= now()`. Задания с отложенным запуском не являются просроченными.
- Просроченные аренды у `running` (и `ready` для обложек); отсутствующая аренда у работающего задания тоже учитывается.
- Задания с **третьей и последующей попыткой** (это признак повторов, не доказательство трёх независимых ошибок), а также `dead`.
- Счётчики должны выводиться даже при нуле; недоступные запросы — **«Нет измерения»**.

**Исполнитель обложек:** код `CoverWorker::run_one` в `tor-ingest` существует, но его запуск в `tor-web/src/main.rs` не подключён. По состоянию таблиц нельзя делать ложный вывод «исполнитель работает». Вывод — «работа не подтверждена»; просроченные, зависшие и окончательно ошибочные задания требуют проверки. Фоновую службу обложек не запускаем автоматически без проверенного S3/контракта и отдельной эксплуатационной приёмки.

**Негативные проверки:** пустая очередь/отсутствующий наблюдатель не изображаются работающим исполнителем; ещё не наступившая `run_after` не считается просрочкой; зависший или трижды ошибочный RIL цикл вызывает предупреждение; `dead` и истёкшая аренда реально видны в PostgreSQL. Операторская страница не должна читать PG и техническое состояние до проверки независимого операторского пароля. Нужны модульные проверки, настоящая PostgreSQL в Actions, браузерная проверка настольной/мобильной страницы и общий набор регрессии.

Не сделано этим изменением: распределённое подтверждение работы исполнителя обложек, внешние уведомления, автоматический запуск/рестарт, установка на VPS и служебные роли сотрудников. Отсутствие данных и признаки проблем не должны выдавать за доказанный отказ сервера.

## OBS-07 — фоновый исполнитель обложек: только явное включение

**Назначение.** Выполнять задания G-07 (PostgreSQL), проверять исходное изображение в закрытом S3, генерировать две WebP-обложки и атомарно прикреплять их через B-контракт. Никаких новых публичных маршрутов, прямых ссылок на S3 или обхода прав автора. Используются существующие lease_epoch и FOR UPDATE SKIP LOCKED.

### Условия запуска

- **По умолчанию выключен.** Только TOR_COVER_WORKER_ENABLED=1 включает один локальный исполнитель в процессе tor-web.
- Требуются PostgreSQL, частный бакет TOR_COVER_S3_BUCKET, сборка с флагом s3-covers и выключенный демонстрационный режим. Невыполненные условия или неверная настройка приводят к явной ошибке запуска.
- Секреты S3 и PostgreSQL задаются вне репозитория. Бакет исключает анонимное чтение.
- Исполнитель запускается после готовности PostgreSQL, читалки и HTTP, не открывает нового пула БД. Цикл с паузой 5 секунд, одновременно не более одного задания в данном процессе.
- Операция ограничена 90 секундами (аренда PostgreSQL составляет 120 секунд). При превышении времени исполнитель **останавливается**, чтобы не запускать вторую операцию параллельно с потенциально ещё работающим вычислением изображения. После рестарта lease и version fence дают возможность безопасно повторить работу.
- Обычные ошибки PostgreSQL/S3 учитываются, после них идут новые циклы. Повреждённый источник уходит в карантин по действующим правилам. HTTP-ответы пользователей не ждут работника.

### Наблюдение

На защищённой странице /ops/overview доступны локальные агрегаты: число циклов, прикреплений, устаревших заданий, карантинов и повторов, ошибок, превышений времени и ошибок подряд. Если цикл не завершался 95 секунд, были три ошибки подряд или исполнитель остановился после превышения времени, показывается предупреждение. Если он не включён, отсутствие наблюдателя не означает, что вся инфраструктура работает исправно.

### Приёмка

1. В изолированной PostgreSQL и испытательном хранилище поставить задание: фоновый цикл выполняется **без ручного вызова run_one**, появляются две проверенные WebP-версии и корректная запись книги.
2. Проверить выключенное состояние, неполные настройки, предел времени и реальную активность местного исполнителя.
3. Сохранить проверки старых сценариев: повтор после просроченной аренды, fence, повреждённая подпись, конкурентное прикрепление, недоступный объект, отзыв доступа.
4. Прогнать Rust, Clippy, форматирование, настоящую PostgreSQL, браузер, обязательные правила и сборку с s3-covers, включая MinIO.

**Ограничение выпуска:** рабочий VPS, его секреты и бакет этим PR не изменяются. Первое включение — только вручную в испытательной конфигурации с контролем памяти (текущий VPS около 1 ГиБ RAM), после проверки восстановления.


## OBS-08 — подтверждение восстановления после краткого отказа S3 и перезапуска исполнителя

Воспроизводимый сквозной тест с **настоящей изолированной PostgreSQL** и управляемым подставным закрытым S3-хранилищем дополняет OBS-07. Он не меняет обработку в боевой среде, права, миграции или формат обложек.

Сценарий:
1. Авторская книга в тестовой базе получает зарегистрированный проверенный источник. Объект временно недоступен в S3, а задание существует в PostgreSQL.
2. **Настоящий фоновый CoverRunner** самостоятельно забирает задание, фиксирует ошибку временной недоступности и сохраняет задание со статусом pending для повторной попытки. Пока изображение не проверено, открытый адрес обложки возвращает 404; слот книги пуст.
3. Первый исполнитель принудительно останавливается (имитация перезапуска процесса). Объект восстанавливается в закрытом хранилище.
4. **Новый экземпляр исполнителя на той же PostgreSQL** после установленной задержки самостоятельно забирает прежнее задание, проверяет исходник и обе WebP-версии, прикрепляет ровно одну ревизию обложки. HTTP теперь отдаёт WebP без публичных ключей S3.
5. Проверяются фактические состояния PostgreSQL, неизменность идентификатора задания, счётчики обоих исполнителей, отсутствие ошибки превышения времени.

Проверка входит в обычный PostgreSQL CI: `cargo test -p tor-web --test cover_worker_pg -- --ignored`. Отдельный тест G-07 уже проверяет истечение аренды, конкуренцию и запрет устаревшему `lease_epoch` завершать работу. Подлинный S3 протокол и анонимный запрет чтения проверяются в отдельном MinIO CI.

**Границы результата:** имитируется остановка задачи в процессе и временная недоступность хранилища; не доказан полный рестарт операционной системы, работа с реальными секретами VPS, пик потребления 1 ГиБ RAM или полный совместный путь PostgreSQL + внешний S3 на испытательном сервере. Эти проверки остаются отдельными требованиями перед включением в рабочей среде.


## OBS-09 — сквозная проверка: настоящие PostgreSQL + закрытый S3

**Зачем:** OBS-07/08 подтвердили автоматическую обработку и восстановление через настоящую PostgreSQL с заменителем S3, а S3-протокол отдельно проверялся MinIO. Это ещё не доказательство, что реальный фоновый обработчик, реальный S3-адаптер и публичный HTTP работают вместе. OBS-09 закрывает этот пробел **только на изолированном испытательном окружении**.

Путь проверки, выполняемый в GitHub Actions без рабочего VPS:

1. Поднять PostgreSQL 18 с разделёнными ролями мигратора и `tor_app`, применить существующие SQLx-миграции и создать одну опубликованную испытательную книгу №950 с владельцем.
2. Поднять MinIO только на `127.0.0.1`, скачать выпуск с проверкой SHA-256 и создать новый закрытый бакет `tor-private-obs09-ci`. Используются только испытательные данные и учётная запись.
3. Реальным S3-клиентом выполнить подписанные PUT/HEAD/ограниченный GET исходного PNG, проверить хеш. Создать долговечное задание в PostgreSQL. До выполнения задания `/covers/950/card.webp` обязан возвращать 404.
4. Запустить настоящий фоновый `CoverRunner`, **без ручного вызова его обработки**. Он должен создать две проверенные WebP-версии в MinIO, записать их в PostgreSQL, атомарно закрепить ревизию 1 за книгой и перейти в `done`. `/covers/950/card.webp` и `/covers/950/main.webp` обязаны отдавать WebP, без перенаправлений и внутренних ссылок на бакет.
5. Подменить содержимое карточки в MinIO, сохранив метаданные SHA-256. HTTP обязан отклонить повреждённое содержимое ответом 503 без тела. После подписанного восстановления правильного объекта — вернуть 200 без увеличения ревизии книги.
6. Из CI сделать прямой **анонимный GET** фактического S3-ключа карточки, полученного из PostgreSQL. Должно быть 403. Это обязательная проверка закрытости реального бакета.

**Внесённые изменения:** `crates/web/tests/cover_s3_pg.rs` (тест запускается только `--features s3-covers -- --ignored`), и единый GitHub Actions `tor-cover-s3.yml`, расширенный PostgreSQL-сервисом. Нет новой миграции, новых внешних маршрутов, изменения прав сайта или автоматического доступа к VPS.

**Критерии приёмки:** все проверки активного SHA, включая Rust, PostgreSQL, браузер, MinIO и отдельное сквозное испытание, должны пройти. Если неудача вызвана неправильным контрактом/правами, исправлять, но **не ослаблять** проверку анонимного доступа, целостности или владельца книги.

**Остаётся за пределами:** действительная работа на выделенном испытательном VPS за HTTPS, замер памяти/процессора при лимите около 1 ГиБ, реальные секреты S3 и проверка аварийного выключения на сервере. Эти пункты обязательны до включения `TOR_COVER_WORKER_ENABLED=1` на рабочем сервере.

## OBS-11 — диагностика ошибок входа без личных данных (28.10.2026)

После случая S002, когда после удачной выкладки страница входа показывала
«Вход временно недоступен», введены **фиксированные счётчики исходов POST
/login**. Обычные HTTP 4xx/5xx не отвечали на вопрос, на каком этапе
произошёл сбой. Ранее смешивались блокировка попыток (429) и ошибка записи
сессии/поиска пользователя (503). Исправление Nginx в PR #165 не заменяет
диагностику причин.

**Где смотреть:** защищённые `GET /ops/overview` (карточка «Вход: причины
ответов», требуется отдельный `TOR_OBS_OPERATOR_PASSWORD`) и `GET /metrics`
(требуется `TOR_METRICS_TOKEN`, Bearer). Секреты и доступ по обычному
пользовательскому cookie не взаимозаменяемы. По умолчанию оба закрыты;
настройка/включение на рабочем VPS отдельно не подтверждена.

`tor_auth_login_outcomes_total{outcome="<fixed-value>"}` — накопительный
счётчик с **десятью фиксированными**, заданными в Rust, значениями:

| Исход | Смысл |
| --- | --- |
| `success` | Сессия успешно сохранена |
| `invalid_credentials` | Неверные или неприемлемые данные; нельзя определить существование email |
| `invalid_form` | Отклонена форма, CSRF или Origin |
| `rate_limited` | Разрешённое ограничение попыток (429) |
| `rate_limiter_unavailable` | Не получилось проверить ограничение попыток (503) |
| `password_pool_busy` | Очередь проверки пароля заполнена (429, повтор позднее) |
| `password_worker_unavailable` | Проверка пароля не выполнилась (503) |
| `lookup_unavailable` | Не удалось прочитать сведения об аккаунте (503) |
| `attempt_reset_unavailable` | Не удалось сбросить счётчик неудачных попыток (503) |
| `session_unavailable` | Не удалось создать сессию (503) |

Один POST /login попадает ровно в **один** исход. Счётчики не записывают
пароли, содержимое форм, email, IP, user ID, query, SQL, cookie и не
добавляют произвольных меток или второй HTTP-маршрут. Счётчики не
переживают перезапуск `tor-web`, об этом написано прямо в интерфейсе.
Рост `session_unavailable` / `lookup_unavailable` даёт конкретное
направление диагностики PostgreSQL, но сам по себе **не доказывает**
точную причину без трассы/журнала. Значение 0 после перезапуска не
означает, что неисправность исчезла.

**Принятие:** модульные проверки 200+ наблюдений и переполнения u64,
ровно десяти статических серий; тесты безопасной выдачи /metrics,
операторской авторизации и числа на странице; действующая PostgreSQL
регрессия POST /login. На испытательном сервере дополнительно проверить
реальную форму входа и записать версию работающего бинарника. Не
переключать рабочий VPS только ради включения диагностики.

## OBS-10 — аварийная остановка и восстановление писателя (изолированный тест)

Тест `crates/observability/tests/trace_store_daemon.rs` поднимает **настоящий
отдельный процесс** `tor-trace-store` с приватным Unix-сокетом `0600` и
одноразовой SQLite-базой. Один и тот же `TracePublisher` проходит:

1. Подтверждённая отправка первой числовой трассы через сокет в SQLite.
2. Принудительная остановка процесса без штатного завершения и проверка,
   что поиск по сокету больше недоступен.
3. Попытка отправки второй трассы во время отказа: вызов HTTP-публикатора
   не ждёт IPC/SQLite, счётчик `failed` возрастает. Потерянная запись
   **не** выдаётся за сохранённую. Отдельный тест на зависший, но
   существующий сокет отправляет 2 000 трасс и проверяет, что очередь
   ограничена, счётчик `dropped` увеличивается и HTTP-путь не ждёт
   ответа SQLite.
4. Повторный запуск нового процесса с **тем же файлом SQLite и прежним
   адресом Unix-сокета** (оставшийся после аварии сокет заменяется).
5. Сохранённая до отказа запись доступна по точному ID с дочерними
   числовыми SQLx-замерами, потерянная отсутствует; новая запись
   доставляется и находится по ID.
6. Счётчики отправителя различают 2 подтверждённые записи, 1 ошибку
   доставки и отсутствие переполнения.

Это **проверка работы отдельных процессов в GitHub Actions**, а не
приёмка запуска под systemd, HTTPS или реального VPS. Она не доказывает
удержание RSS/CPU в пределах бюджета ~1 ГиБ либо устойчивость при
перезапуске операционной системы и разрыве электропитания. Полное
испытание OBS-10 остаётся незакрытым до отдельного тестового окружения
с systemd, отключением службы и оценкой памяти. Не активировать
`TOR_TRACE_STORE_SOCKET` на рабочем TOR этим изменением.
