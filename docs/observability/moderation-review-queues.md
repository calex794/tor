# TOR / MOD-UI-01 — работа с очередями модерации

Статус: операционная инструкция для разработчиков и дежурных. Не является
включённым мониторингом, автоматическим уведомлением или разрешением менять
постоянную базу. Новые требования к SLA должны быть отдельно приняты.

## Что находится в кабинете

| Очередь | Интерфейс | Источник истины | Решение |
| --- | --- | --- | --- |
| Регистрация | `/moderation/books/registrations` | `books` и `book_registration_decisions` | Принять/отклонить регистрацию, не публикуя черновик |
| Обложки | `/moderation/covers` | `book_cover_review_requests` | Принять конкретный staged-кандидат либо сохранить прежнюю обложку |
| Удаление | `/moderation/books/deletions` | `book_ordinary_deletion_requests` | Завершить обычное удаление или восстановить прежнюю видимость |
| Рассмотренные | `/moderation/books/reviews` | append-only decisions всех трёх типов | Только просмотр, без повторного одобрения |
| Контроль | `/moderation/books/control` | отдельные hold/visibility события | Экстренные ограничения, **не** решение заявки |

Только действующие модераторы **сайта** и администраторы. Модератор внутри
команды книги не получает права просмотра журнала и принятия решений.
У каждого решения свои ID заявки, ревизия, исполнитель и время. Нельзя
подменять рассмотрение регистрации ручной правкой `visibility_status`.

## Проверка очереди

1. Открыть соответствующую вкладку, проверить серверный счётчик, фильтры и
   следующую страницу. Поиск и фильтры применяются к БД до ограничения 40
   записей, поэтому пустая страница поиска сама по себе не означает пустую
   очередь.
2. Для обложки проверить защищённый предпросмотр и тип: первичная или замена.
   Публиковать необработанный S3-объект либо URL кандидата напрямую нельзя.
3. Перед решением сверить ID книги/заявки и ожидаемую ревизию. Для отказа
   указать конкретную причину. При наличии шага подтверждения перечитать
   последствия перед финальной отправкой.
4. После действия обновить очередь и убедиться, что заявка снята с ожидания,
   а решение появилось в приватном журнале. Нельзя считать действие успешным
   лишь по нажатию кнопки.
5. При `409` — другой модератор уже принял решение или ревизия устарела:
   перечитать очередь, **не** повторять старый POST. При `403` — проверить
   действующую site-role/сессию, не обходить запрет. При `503` — проверять
   здоровье PostgreSQL/хранилища и эскалировать; не выполнять слепое массовое
   одобрение.

Отказ в удалении восстанавливает прежнюю видимость по серверному решению;
сама заявка автора может скрывать книгу немедленно. Одобренное обычное
удаление не должно уничтожать ранее закреплённые бесплатные или купленные
V1 в личных библиотеках. Правила жёсткой блокировки, возвратов и возрастных
прав действуют отдельно.

## Возраст книги не равен времени ожидания

Фильтр `basic / adult / pro_adult / legacy` относится к **возрастному
ограничению содержимого**. Для операционного контроля требуется отдельная
величина `waiting_age = now() - submitted_at`. Не называйте фильтр
категории 18+/21+ фильтром старых заявок.

В схеме есть исходные временные поля:
- регистрация: `books.created_at` (для повторных заявок это лишь дата книги,
  а не отдельного повторного обращения);
- обложка: `book_cover_review_requests.submitted_at`;
- удаление: `book_ordinary_deletion_requests.requested_at`.

Пока нет независимых записей повторной подачи регистрации, `created_at`
нельзя использовать как точный SLA для повторного рассмотрения.

## Диагностика только чтением

Следующий запрос — пример для изолированной read-only проверки оператором
БД, не публичный endpoint и не автоматизированный alert. Он соответствует
текущим условиям трёх pending-очередей; список доступных конкретному
модератору заявок может дополнительно исключать его собственные книги.

```sql
WITH pending AS (
  SELECT 'registration'::text AS kind, id AS request_id,
         created_at AS requested_at
  FROM books
  WHERE registration_requires_review
    AND visibility_status = 'pending_moderation'
    AND registration_approval_decision_id IS NULL
    AND NOT is_deleted

  UNION ALL

  SELECT 'cover'::text, id, submitted_at
  FROM book_cover_review_requests
  WHERE state = 'pending'

  UNION ALL

  SELECT 'deletion'::text, r.book_id, r.requested_at
  FROM book_ordinary_deletion_requests r
  JOIN books b ON b.id = r.book_id
  WHERE b.lifecycle_status = 'pending_deletion'
    AND b.lifecycle_revision = r.request_revision
    AND NOT b.is_deleted
    AND NOT EXISTS (
      SELECT 1 FROM book_ordinary_deletion_decisions d
      WHERE d.book_id = r.book_id
        AND d.request_revision = r.request_revision
    )
)
SELECT kind, count(*) AS pending_count,
       min(requested_at) AS oldest_pending_since,
       round(extract(epoch FROM (now() - min(requested_at))) / 3600.0, 1)
         AS oldest_age_hours
FROM pending
GROUP BY kind
ORDER BY kind;
```

Этот запрос не должен выполняться с публичными SQL-правами и не должен
попадать в пользовательские API, где появились бы внутренние данные очереди.

## Предлагаемая политика сигналов (не включена)

До утверждения продуктом и включения мониторинга используем пороги как
рабочую гипотезу: предупреждение при возрасте нерассмотренной заявки
более 24 часов, критический сигнал — более 72 часов; отдельный сигнал
при устойчивом росте очереди три наблюдения подряд. Для регистрации
следует учитывать оговорку о повторной подаче выше.

Нужны отдельные источники/владельцы сигналов, графики по трём типам,
согласованная периодичность проверки и проверка того, что роли и имена
модераторов не появляются в публичной телеметрии.

## Служебный журнал просрочки — этап #661, без доставки

Отдельная таблица `moderation_overdue_signals` и ручной внутренний метод
`PgAccounts::scan_moderation_overdue_observations(batch_limit)` фиксируют
пороговые наблюдения, если модерационная заявка оставалась ожидающей
24 или 72 часа. **Ни маршрута, ни расписания запуска, ни почты, ни push,
ни автоматически отправляемых уведомлений на этом этапе нет.**
Созданная миграция предназначена для изолированного CI и не раскатывается
на постоянные базы без отдельного решения.

Уникальный ключ — тип заявки + идентификатор + ревизия запроса +
порог 24/72 часа. Для первой регистрации используется id книги с
ревизией 0 (новой повторной заявки в модели пока нет); у обложки
используется уникальный id заявки; у удаления — id книги и ревизия.
Параллельные сканирования сериализованы PostgreSQL advisory lock,
первое наблюдение сохраняется, повторные вызовы не создают дубликатов.
После решения или снятия заявки открытые наблюдения помечаются
`resolved`, не удаляя историю. Если модерация завершилась одновременно
со сканированием, при следующем вызове запись будет сверена заново —
будущий доставщик обязан дополнительно проверять живое состояние перед
отправкой.

В служебной таблице нет текста книги, email, имени автора/модератора
или staging-ключей. Это не система SLA: получатели, доставщик, временные
зоны, повторные заявки и оповещения остаются несогласованной частью
#661. Операционные пороги 24/72 часа пока не утверждены.

## Критерии закрытия MOD-UI-01

- Реальный PG/HTTP + Chromium: две конфликтующие ревизии, `409`, отказ в
  правах после отзыва site-role, CSRF/Origin negative, клавиатура и экраны
  390px/1440px.
- Все три типа решения требуют явного подтверждения человеком в UI;
  первичный шаг не изменяет данные. Прямой привилегированный запрос всё равно
  должен защищаться серверными правами/ревизиями.
- После каждого решения счётчики обновляются, причина отказа видна только
  соответствующему автору, личность модератора только site-role.
- Реальный фильтр **времени ожидания**, отдельно от контентного возраста;
  подтверждённый механизм сигналов и дежурства.

Production, VPS и постоянные базы не меняются этой инструкцией.
