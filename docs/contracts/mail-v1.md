# MAIL — outbound system email

Decision: 26 November 2026. Keep password-based registration and sessions. No email-code login. This is a new outbound channel, not the existing internal /mail conversations.

## MAIL-01 (I/G): durable reference queue

Registration confirmation, password reset, support reply notification and project news are the only purposes. Password reset is a separately gated transactional purpose; no passwordless login. A single trusted event/recipient/purpose is unique. The queue stores numeric references, no addresses, message text, tokens or secrets. Claim is atomic, bounded and prioritized; no database transaction stays open during network I/O. A stale generation or expired claim cannot finalize a row. SMTP acceptance is not delivery. Expired claims become uncertain and cannot be blindly replayed. No live dispatch or HTTP integration in this change.

The first isolated PostgreSQL test is `cargo test -p tor-mail --test slices_pg -- --ignored` with migrated disposable local tor_ci, plus `cargo test -p tor-mail -p tor-contracts`. The dedicated test must be wired into the applicable PG CI before acceptance.

## MAIL-RESET — password recovery by email

- RESET-01a: introduce the explicit reset purpose, request-bound quota evidence and independent recipient/IP cooldowns (3 per rolling 24h per recipient, 120 seconds between attempts, 10 per rolling 24h per verified IP; unknown IP shares a bucket). All purposes share provider pacing, daily cap, recipient suppression and monthly cost guard. No source producer, worker or external delivery in this slice.
- RESET-01b: account-owned source repository and handoff contract. One source per active account, at most one new source per 120 seconds, 10-minute source expiry, fresh numeric event identity on replacement. Changing credentials, email or account state deletes the source. Store only keyed mailbox/IP evidence and the credential fingerprint, never a reset token or raw email/IP. Reconcile at most 100 unforwarded references per scan; mark forwarded only after the idempotent mail queue has durably accepted the reference. A stale/expired source must cancel the queue claim. The worker must resolve the exact current source and use the signer to match the current transport address before quota admission. Existing usable reset tokens are not revoked by a source request. HTTP wiring and generic acknowledgement remain a subsequent slice; no sender or source producer is activated.
- RESET-01c: explicit staged queue ingress with both TOR_PASSWORD_RESET_ENABLED=1 and TOR_PASSWORD_RESET_QUEUE_ENABLED=1 plus the existing nonzero 256-bit TOR_MAIL_QUOTA_KEY. No fallback to the historical sendmail adapter if queue mode is selected, including invalid key/flag configuration. Old MTA path remains for HTTP loopback test fixtures only. Origin/CSRF and distributed auth throttles apply; bounded asynchronous account lookup and source capture happen outside the identical acknowledgement path. A separately managed, bounded five-second handoff loop runs only in opted-in authenticated PostgreSQL mode; acknowledge after the idempotent enqueue result (including existing reference) so lost receipts replay safely. No token is generated by ingress or handoff. No new HTTP route, no SMTP and no production enablement before RESET-02 through RESET-04. Stale queue references must be cancelled by the later delivery worker, which must re-resolve the exact current source before sending.
- RESET-02a: final admission and proof issuance share the existing Postbox correlation transaction. The common reservation, cost policy, lease, suppression and month checks remain mandatory. Lock quota guard, account, then outbox/source/proof; recheck source event, active account, credential fingerprint, keyed recipient/IP and key binding against the durable reservation and correlation. Generic prepare cannot issue a password-reset send permit. A caller supplies only the SHA-256 digest of a fresh 256-bit in-memory proof after successful quota reservation; issue once per source event, with a 30-minute database-clock expiry, atomically with the correlation. Never revoke an older usable proof merely to issue a new one. Changing password, email or account state revokes all outstanding proofs; request replacement/expiry alone does not. No network or sender in this slice.
- RESET-02b: integrate the existing MAIL 2/6 Lettre/Rustls transport, not a second SMTP client. The reset-specific renderer accepts a validated configured HTTPS DNS origin and a fresh 43-character A-07 secret; the shared MIME adapter builds the one-recipient message with the durable correlation marker. The fragment never enters HTTP request URLs. No raw proof in PostgreSQL, logs or queue. Final admission requires at least 25 seconds left on the lease before the common 20-second submission deadline. The reset-specific terminal transaction matches the exact outbox generation, event, account, identity, quota-key binding and digest; definite nonacceptance/cancellation revokes only its own proof, accepted/uncertain preserves it; provider ID conflicts do not authorize replay. No quota refund or automatic retry. Loopback SMTPS and disposable PostgreSQL tests only. MAIL gate 4 owns the single common worker, recipient preflight, fresh secret generation via A-07, authenticated session, final launch/send-start fence and bounded scheduling; do not activate ingress or dispatch before gates 3–6. This combined integration branch includes the accepted main recipient preflight and cost reconciliation plus gate 2 transport; no parallel sender or provider connection at runtime.
- RESET-02c / MAIL 4a: combine the reviewed operator gate with recovery; a process-local DispatchGrant binds the exact leased claim to one current dispatch activation and one expected monthly counter increment. The guarded quota transaction persists the immutable activation digest on the reservation. Final correlation/proof preparation requires that same digest, exact current activation/profile/DB/month/budget, exact identity and current counter; an operator-test receipt or the legacy standalone admission path cannot authorize a live dispatch. Match account-first lock order used by admin activation and credential changes. Final preparation returns a non-cloneable PreparedDispatch witness only after commit; the database's final read checks the exact lease, correlation marker, bound reservation, active recipient, suppression, current budget/profile and (for reset) exact still-live proof and source. A typed DispatchStart then consumes the process approval's one expected increment, within four seconds of the beginning of final preparation and with a 21-second lease margin for the 20-second submission timeout. The worker must share one LaunchFence and serialize these checks and SMTP start; raw counters cannot authorize dispatch; actual worker startup, deferred scheduling, activation route and operator test-send remain separate. No runtime sender in this slice.
- RESET-02d / MAIL 4b: one common durable scheduler. Only registered source purposes are claimed. Pre-charge DNS/transport/pace/cooldown deferrals use a distinct deferred state, database-clock due time, bounded 30/60/120-second backoff for DNS/transport/activation, a redacted diagnostic reason, at most four claim generations, and the original queue creation time (10 minutes for reset, 24 hours for other flows). The common budget lock serializes deferral with reservation/correlation; any reservation or feedback for the row forbids retry. No refund, generation reset or automatic replay of expired leases, even if a worker died before SMTP. All stale/foreign claim completions fail closed. No activation or provider connection in scheduler tests.
- RESET-02e / MAIL 4c: common serial dispatch driver with a trusted source port. The only installed product handler in this slice is password recovery; other purposes remain untouched until their source and consent gates exist. One shared process fence serializes all worker handles, rejects stopped/test-only state before claiming, and holds no database transaction over DNS or SMTP. Resolve the exact active source and perform recipient preflight, load/decrypt the approved profile, authenticate SMTPS, re-resolve the source, then reserve shared quota and mint a fresh A-07 secret. Prepare the correlated proof and MIME under the exact charged recipient key, recheck the typed send-start witness, consume the process grant immediately before the single-use SMTP submission. Pre-charge DNS/connect/pace failures may defer; post-charge failures stop the fence when its counter cannot be safely consumed, without refund or replay. Lost acknowledgement or timeout is uncertain, never an automatic retry. A bounded explicit run loop stops between attempts on shutdown; not connected to startup or an admin activation route. No external provider connections in tests.
- RESET-03a / MAIL 4d: explicit server-owned managed runtime, disabled unless TOR_MAIL_DISPATCH_WORKER_ENABLED=1 and authenticated PostgreSQL, both reset queue flags, valid quota key, profile master key, HTTPS origin and configured system DNS are present. Start exactly one stopped LaunchFence and one recipient cache; reuse the current Postbox transport and shared pool. The router gets the same process control via an extension; validated administrator stop/limit/reconciliation/profile changes revoke local approval before the database mutation. No activation endpoint in this slice. On SIGTERM/interrupt, retire this authority irreversibly before HTTP drain, signal the worker and join the bounded current attempt (95-second join limit); listener errors do the same, and unexpected abort never permits replay. Other background tasks remain independently cancellable. Unit tests use only local tasks and fake signals, no DNS/SMTP. Deploy-time service stop budget must allow worker drain plus other collectors (at least 130 seconds); production configuration unchanged. Existing account recovery addresses use disposable policy Observe rather than retroactively applying registration rejection.
- RESET-03b1: exact stopped review preparation for the future activation UI. Read the live administrator, shared quota lock, reconciled stopped snapshot and sealed candidate in one transaction; the encrypted candidate digest must match the snapshot. Repeat after any non-sending probe. A non-consuming process-local precheck rejects foreign session/challenge/mode, stale snapshot, wrong billing evidence and expired/retired review before provider I/O or password work. It does not create an intent, arm the worker or replace confirm_review and the durable exact-intent step-up transaction. Tests cover no reconciliation, enabled policy, unauthorized session and precheck invalidation. No new HTTP route, activation, real SMTP or deployment in this slice.
- RESET-03b2: two explicit administrator POST routes for dispatch review/confirmation, visible only with the opted-in managed runtime, stopped policy and a saved profile. A live role and same-origin CSRF guard are mandatory. Review displays the exact bound budget/profile/evidence metadata, creates a process/session-bound five-minute challenge, never enables mail. Confirm requires explicit evidence and consent, exact non-consuming precheck before password work, bounded password verification, shared non-sending SMTPS probe with the existing three-per-minute per-actor probe quota, then fresh coherent candidate/role/budget observation. Consume the review, issue a separate exact-intent password proof, commit admin_activate, re-read the receipt and complete only the current process fence. A failed/ambiguous commit or interrupted local completion cannot authorize this attempt; explicitly stop and reconcile before retry, never roll back an unknown/newer revision automatically. The displayed evidence hash is not independent verification. Added RIL route registry/exposure/guard evidence and negative mutation tests; no-runtime HTTP denial checks use disposable PostgreSQL and never contact the provider. Operator-only test-send, managed-runtime concurrent HTTP/loopback acceptance, and current-main integration acceptance are still prerequisites to merge and rollout. No real Postbox calls, credentials, VPS change or deployment in this slice.
- RESET-03: verify real PostgreSQL, HTTP and Chromium flows (unknown email, expired/replayed/wrong token, session revocation, provider failure, concurrent requests, restored stale database and budget stop). Retire or fence the old local sendmail path before enabling production email reset; it bypasses MAIL-01 quotas.
- RESET-04: operator-approved Postbox staging and inbox acceptance; no real delivery in CI or automatic deploy. Telegram and backup codes are separate deferred recovery methods.

## Subsequent acceptance gates

- MAIL-02: secure SMTP adapter with a maintained MIME/TLS library; first provider Yandex Cloud Postbox, fixed postbox.cloud.yandex.net:465 (SMTPS) or 587 (STARTTLS required). No plaintext fallback; bounded timeouts, static/redacted errors; local mock SMTP acceptance/rejection/ambiguity tests; safe retry only after definitive non-acceptance. Operator controls both activation and quotas. Respect 200/day and 1/sec until provider approves higher quotas.
- MAIL-03: /odmen email provider configuration, admin authorization, Origin/CSRF, encrypted credentials with versioned recovery key, test-send separate from activation; no secrets in HTML, logs, GitHub or database dumps without encryption. Reuse established S3-admin security patterns without reusing its key.
- MAIL-04: worker startup opt-in, source-event integration, retry scheduling, limits and bounded retention, provider failure independent of the website. The renderer must recheck account/source ownership and news subscription immediately before SMTP; pending references must not bypass that check.
- MAIL-05: registration confirmation via one-time verification link (not authentication); preserve existing password and session behavior. Token storage and expiry belong to accounts. Do not force existing accounts to re-register. A future activation-policy change needs a separate decision.
- MAIL-06: outgoing support reply notification, no private conversation text in email; authenticated link back to the site. Guest support remains functional without a mailbox. Receiving replies at support@ requires separate inbound email routing/mailbox; Postbox alone is outbound only.
- MAIL-07: opt-in site news, explicit unsubscribe, send once per publication, recheck consent at dispatch, no automatic subscription on registration. News cannot exhaust capacity reserved for transactional messages; batch/checkpoint and abuse controls.
- MAIL-08: real VPS/Postbox SMTP acceptance and inbox delivery, monitoring, restore credentials and queue from backup, manual production deployment from checked main. No automatic deploy or real emails in CI.

Sources: existing TOR decisions-v1/api-v1/data-and-events, account registration and support service; Yandex SMTP documentation https://yandex.cloud/ru/docs/postbox/operations/send-email . DNS and live credentials are not part of the repository.
