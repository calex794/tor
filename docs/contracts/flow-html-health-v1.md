# FLOW-02/06/09 — подтверждение записи анонимных HTML-агрегатов

Этот контракт описывает долговечное подтверждение анонимных HTML-агрегатов.
Предметные, PostgreSQL, HTTP, браузерные и процессные проверки обязательны на
точной общей ревизии. Результаты конкретного SHA фиксируются в приёмке PR и
после слияния; наличие тестов не заменяет их успешное выполнение.

Владелец — `tor-traffic_behavior`; F получает его ограниченный read-only отчёт
через web composition. Этот пакет дополняет `flow-observation-hours-v1.md` и
`flow-data-signals-v1.md`. Персональных событий, согласий, IP, cookie, URL и
читательских идентификаторов нет. Epoch обозначает серверного исполнителя
сбора, а не человека.

## Какое свидетельство сохраняется

Наличие строки `ril_flow_observed_hourly` говорит только о сохранённых ответах.
Оно не доказывает непрерывность сбора в течение часа. Локальный пустой успешный
цикл, ноль потерь нового процесса и все 24 строки также не доказывают качество
предыдущего периода.

`ril_flow_health_epochs` хранит начало, подтверждённую границу, срок аренды,
поколение, ожидаемую границу, признак завершения и накопленные числовые счётчики
потерь/ошибок. `ril_flow_health_hourly` хранит только признаки потерь и ошибок
по часам. Счётчики текущего процесса показываются отдельно; их нельзя делить
на общий отчёт и называть долей охвата.

Один цикл существующего RIL pump:

1. Получает ограниченную аренду и DB-clock checkpoint. Соединение освобождается.
2. Ставит FIFO-барьер в существующую очередь. Неблокирующий `try_lock` удерживается
   только во время постановки; SQL и ожидания ответа под ним нет. HTTP использует
   тот же краткий барьер вокруг часов и `try_send`, поэтому приостановленный
   producer не может оказаться за подтверждённым барьером.
3. Сохраняет обычный неизменяемый RIL UUID и дожидается `status=done` именно этого
   пакета. Четыре materialization за проход — прежняя ограниченная работа.
   Успешный enqueue ещё не подтверждает запись итогов. Пустой drain — отдельный
   упорядоченный ответ очереди, после которого тоже требуется SQL ACK.
4. В одной SQL-транзакции проверяет epoch, поколение, живую аренду, DB clock
   и `done` пакета. Если у пакета есть staged FLOW rows либо ненулевой
   `flow_observed_discarded`, обязательна его неизменяемая observed receipt.
   Только технический пакет без FLOW может не иметь такой квитанции. Отсутствие
   обязательной receipt не превращается в ноль потерь и не продвигает границу.

FIFO-барьер ставится синхронным `try_send`, без `spawn_blocking`. Ответ через
oneshot остаётся полем pump при отмене или тайм-ауте цикла. Поздний ответ
сохраняет пакет один раз, но подтверждает только свой полный checkpoint
(epoch, generation и cut), а не новую эпоху или границу. Если получатель уже
закрыт, worker возвращает пакет в текущий агрегат до следующего FIFO-сообщения.

Потери и ошибки сохраняются независимо от ожидания `done`: известный отказ
записи не исчезает после перезапуска. Поскольку точное время каждой потери не
хранится, признаки консервативно помечают пересекающиеся часы, включая граничный
час округлённой миллисекунды. Эти признаки — не точное число потерянных ответов.

## Первая регистрация и промежуток между исполнителями

Recorder сохраняет монотонное время своего создания. После восстановления
readiness сервис получает DB-clock sample, а затем измеряет прошедшее от начала
пропуска монотонное время. Вычитание этого возраста из более раннего DB sample
даёт консервативную нижнюю границу пропуска, включая задержку ответа SQL.
Возраст округляется вверх; sample БД — вниз. Добавляется одна миллисекунда
запаса. Здесь не предполагается, что задержка запроса равна нулю или заранее
известной величине.

Одна транзакция записывает закрытый неподтверждённый интервал до регистрации,
сохраняет известные ещё не учтённые потери/ошибки и создаёт новую живую эпоху.
Только после успешной транзакции сервис двигает свой cursor учтённых счётчиков.
Начальный baseline новой эпохи не поглощает потери при запуске. Сам интервал
остаётся неизвестным даже при отсутствии зарегистрированной потери.

Для регистрации runtime создаёт случайный `registration_key` на одну попытку
создания исполнителя. Ключ не связан с посетителем. PostgreSQL сериализует
повторы этого ключа короткой advisory-блокировкой и уникальным ограничением.
Если commit прошёл, а ответ потерян, повтор возвращает уже созданную эпоху и
её фактически записанный baseline счётчиков. Новый gap или orphan epoch при
этом не появляется. Потери, накопившиеся до получения ответа, не исчезают:
следующий note сравнивается с возвращённым сохранённым baseline. При смене
известной эпохи ключ меняется; при неизвестном исходе транзакции сохраняется.

Этот механизм относится к зарегистрированным исполнителям. Он не доказывает,
что каждый HTTP-процесс установки вообще зарегистрировался. Начавшийся, но
никогда не связавшийся с БД процесс не становится автоматически известным другим
исполнителям; полнота всей установки не утверждается.

## Часы и срок аренды

Аренда — 30 секунд; producer дополнительно прекращает HTML-сбор по монотонным
часам через 25 секунд от начала запроса к БД. Технический RIL и основной
HTTP-ответ продолжают работать.

Для проверки времени сохраняются монотонные точки до SQL и после ответа.
Само чтение системных часов тоже ограничено монотонными точками до и после.
Округлённый DB sample с учётом его миллисекундной неопределённости задаёт нижнюю
и верхнюю границы возможного времени БД. Timestamp принимается только в
пересечении [верхняя граница − 2 секунды, нижняя граница + 2 секунды].
Так отклонение остаётся в пределах двух секунд при любом допустимом моменте
DB sample. Интервал неопределённости шире четырёх секунд не проходит проверку.
Расчёт использует наносекунды, включая граничные случаи округления.

Отклонение даёт потерю измерения, а не выдуманное время. Подтверждённая граница
отстаёт от DB cut на две секунды. Будущий допустимый producer поэтому не
добавляет ответ в уже подтверждённый час.

Ожидание пакета продлевает только живую аренду, не подтверждённую границу.
Максимальный возраст checkpoint — 120 секунд. Истёкшая эпоха не возобновляет
подтверждение старого промежутка.

## Смена исполнителя и окончательная остановка

Истечение аренды не доказывает прекращение HTTP. При Expired сервис закрывает
локальный gate и сохраняет identity собственного predecessor. В БД predecessor
остаётся незавершённым, поэтому остановившийся между попытками сервис не исчезает
из проверки покрытия. Другой здоровый исполнитель не может закрыть этот хвост.

При успешной повторной регистрации одна транзакция с общим DB instant сохраняет
известные отказы predecessor, закрывает его фактический интервал, записывает
неподтверждённый gap и создаёт successor. Нет зафиксированного состояния со
старой закрытой эпохой и ещё не созданной новой. Ошибка до commit откатывает
все части. Неизвестная история не заполняется новыми ACK.

Сервис заменяет только своего predecessor, identity которого сохранилась в
памяти того же процесса. Поиска и автоматического retire всех истёкших epochs
нет. Запуск другого процесса не доказывает остановку предыдущего.

Для отдельного terminal retire владелец HTTP сначала прекращает приём запросов
и дожидается завершения всей in-flight middleware. Только затем допустим
`PgRollupPump::shutdown(HtmlIngressStopped)`; witness создаёт владелец HTTP
через `HtmlIngressStopped::after_http_stopped_and_drained()`. Метод потребляет
pump, пробует один заключительный ограниченный цикл и затем сохраняет retire.
Незавершённый пакет не превращается в подтверждённый. Для фонового выполнения
`spawn_with_shutdown(receiver)` принимает witness между завершёнными циклами;
закрытие канала без witness оставляет эпоху unresolved. Закрытие producer или получение SIGTERM сами по себе
не являются таким свидетельством. Drop, abort и panic без подтверждённой
остановки HTTP закрывают локальный gate, но оставляют epoch незавершённым.
Durable RIL-пакеты по-прежнему доступны другому pump для штатного точного повтора.

В `flow_runtime` witness передаётся после успешного возврата Axum graceful
shutdown. Процессная проверка `tools/flow_lifecycle_pg.cjs` удерживает настоящий
HTTP-запрос блокировкой PostgreSQL, посылает SIGTERM и проверяет, что listener
уже закрыт, а HTML/card epochs ещё не завершены. После освобождения запроса
проверяются сохранение последнего ответа и карточки ровно один раз и завершение
всех созданных процессом эпох, включая successor. Отдельный SIGKILL оставляет
эпохи unresolved. Изолированные pump-тесты не заменяют эту проверку.

## Периодный отчёт и административный путь

`PgFlowAudience::observed_health_report(days, zone)` возвращает сохранённые
HTML-числа и `Option<HtmlHealthReport>`. Числа, capability и health читаются в
одной `REPEATABLE READ READ ONLY` транзакции с общей UTC-границей. Более поздний
ACK не может удостоверить числа из более раннего снимка. Допустимы 1/7/30/90 дней,
два соседних окна завершённых часов, максимум 4320 часов. Часовой пояс БД не
меняет UTC-границу; выбранная зона меняет только отображение. Обе части используют
время одной транзакции. Числа удерживают все 180 завершённых дней, включая точную
нижнюю границу; health не подтверждает часы старше этого retained окна даже при
более раннем переданном anchor.

Если обе health-таблицы отсутствуют и health-миграция не отмечена успешно
применённой, доступные старые числа сохраняются с `None` для качества.
Частичная схема, успешно применённая миграция без таблиц, таблицы без успешной
миграции или ошибка чтения установленного журнала остаются ошибкой.
SQL failure не превращается в fallback со здоровым нулём. Если отсутствует
сам источник наблюдаемых чисел, история не выдумывается.

Час подтверждён, когда объединение подтверждённых интервалов покрывает его
целиком **и каждый зарегистрированный исполнитель**, пересекающий час,
подтвердил свою часть. У незавершённого epoch интервал участия не заканчивается
при истечении lease. Для него требуется подтверждение до конца проверяемого часа.
Возраст записи и чистый новый процесс этого требования не снимают.

Это свидетельство данного механизма зарегистрированных исполнителей; не
полнота всех процессов установки, не число людей и не измерение запросов,
не дошедших до приложения. История до журнала не восстанавливается. Readiness
старой схемы закрывает управляемый HTML-сбор, сохраняя технический RIL.

«Аудитория» показывает отдельно подтверждённые часы, часы с потерями и часы с
ошибками для обоих окон. Локальные счётчики сохраняют подпись своего ограничения.
При отсутствующей старой capability доступные числа показываются с явным
неизвестным качеством. Ошибка чтения установленного журнала даёт 503 и явное
отсутствие диагностики. GET не создаёт ACK и не меняет состояния. Сохраняются
живая роль администратора, private/no-store, noindex и формы без JavaScript.

SQL — 750 ms, lock timeout — 75 ms; общий HTTP предел — 950 ms. Цикл pump
ограничен 6 секундами, операции health — 950 ms, пауза между циклами — 10 секунд.
Соединения не удерживаются при ожидании очереди. Это пределы ограниченного
асинхронного выполнения, а не гарантия исполнения планировщика в реальном времени.

`html_quality` и `html_change` используют долговечные подтверждённые часы вместо
количества строк. Потери/ошибки любого сравниваемого окна запрещают сравнение.
Полностью подтверждённый пустой интервал может дать известный ноль сохранённых
ответов; неполный или потерянный интервал — нет. Отсутствующая capability не даёт
Healthy. Unknown не завершает старый эпизод. Пороги изменения относятся только
к сохранённым ответам.

## Удержание

Часовые признаки и закрытые epochs удерживаются 181 день, покрывая два
90-дневных окна. Очистка за проход — не больше 500 часовых строк и 100 старых
**закрытых** epochs. Возврат долго отсутствовавшего процесса ограниченно
помечает только удерживаемое окно, не расширяет историю.

Незавершённые epochs не удаляются только из-за возраста lease. Без
доказанного lifecycle witness их интервал остаётся неизвестным, в том числе
дольше 181 дня. Такой исполнитель может приостанавливать сравнение бессрочно;
новый процесс и очистка не объявляют его остановленным.

## Предметная и интеграционная проверка

Подготовлены PostgreSQL scenarios для точного materialized batch, пустого ACK,
конкурентного повтора, поколения и истёкшей аренды; потери до первого readiness
и после retire; gap на границе UTC; пропавшего A при здоровом B в обоих окнах;
сохранения unresolved epoch при prune; последней миллисекунды; UTC при
`Asia/Kathmandu`; блокировки materialization и регистрации; повторной записи.

Отдельные scenarios проверяют done FLOW без receipt, допустимый technical batch
без FLOW, discard-only FLOW, отсутствие capability при сохранённых числах,
частичную или повреждённую схему и отказ чтения установленного журнала.
Atomic handoff проверяется после service Expired до нового prepare, при
откате заблокированной транзакции и при общем DB instant успешной замены.

Детерминированные unit cases проверяют оба знака clock offset, обе границы
двухсекундного допуска, соседнюю наносекунду, RTT 3999/4000/4001 ms, прежнее
ложное принятие +2.9 секунды и включённую верхнюю часовую границу потери.

HTTP-проверки охватывают read-only, различие отсутствия capability и ошибки
установленного журнала, private/no-store и ограниченный 503. Браузерный сценарий
`tools/audience_html_health_pg_browser.cjs` открывает настоящую страницу и
диагностический блок на 390/1440 без JavaScript, меняет периоды и часовой пояс,
проверяет неизвестное измерение, подтверждённый ноль, потери и отзыв доступа.
Он запускается сразу после свежих миграций до остальных предметных fixtures;
чужие сохранённые данные и незавершённые epochs ради сценария не удаляются.

Регистрационные PostgreSQL-сценарии повторяют успешный запрос после утраты
первого результата, проверяют конкурентный retry, сохранённый baseline потерь,
единственного successor и повреждённую capability без registration column.
Это модель неоднозначного ответа, а не заявленная сетевая fault injection.

Весь `ril_rollups_pg` также охватывает отсутствующий witness, abort фонового
pump, конечный цикл при остановке, исключение текущего частичного часа и точную
нижнюю границу 90+90 дней. Обязательные гейты включают строгий Clippy, реальное
обновление установленной схемы с сохранением checksum, replay миграций и
процессный stop/drain. Приёмка выполняется на окончательном объединённом SHA.
