# TOR / Shadow — ручная публикация и SEO двух доменов, v1

**Статус:** первый безопасный срез в TOR: схема PostgreSQL, ограниченные
читательские представления и типизированная SEO-политика. **Это ещё не
самостоятельный сайт Shadow и не включённая индексация.** До отдельных
GET-маршрутов, интерфейса ручного переключателя, отдельной роли/секрета,
проверки реальной поисковой выдачи и одобрения РСЯ остаются шаги.

Опорное исследование: [Петля 8 в Notion](https://app.notion.com/p/3db32a84beec81c4a8ded8e259ed8e0b),
[архитектура TOR + Shadow](https://app.notion.com/p/40632a84beec818481f5c82f4e258070),
[SEO-пилот](https://app.notion.com/p/40632a84beec81349131dcf40ce80b12).

## 1. Продуктовое решение

- Ровно одна Book, один источник глав и метаданных: основное TOR/NEwBOO.
- Владелец вручную включает книгу в Shadow: books.shadow_enabled, по умолчанию
  FALSE. Само наличие неоплаченной главы **не** включает её в Shadow.
- Включение не сканирует и не запрещает смешанные книги: цены глав основного
  сайта не определяют право на отдельное бесплатное размещение владельцем.
- Публикация/админ-блокировка/удаление книги и главы остаются обязательными
  условиями просмотра; прямая ссылка не даёт обход.
- Обе витрины могут быть доступны читателю, но одинаковые страницы должны
  иметь одну заранее выбранную поисковую роль.

## 2. Два независимых переключателя

| Поле | Начальное значение | Смысл |
| --- | --- | --- |
| books.shadow_enabled | false | Владелец разрешил публикацию книги в Shadow |
| books.seo_index_owner | pandaolate | У какого сайта приоритет индексации книги |

SEO-роль **не переключается автоматически** при разрешении книги для Shadow.
Это защищает уже индексируемые страницы Pandaolate от внезапного noindex.
Чтобы сделать Shadow поисковым владельцем, администратор отдельно устанавливает
seo_index_owner=shadow. PostgreSQL запрещает состояние owner=shadow при выключенном
shadow_enabled. Выключая Shadow, нужно **одним UPDATE** установить
shadow_enabled=false и seo_index_owner=pandaolate.

Состояния:
- нет ручного разрешения: Shadow не публикует книгу;
- разрешена и SEO-роль pandaolate: книга доступна в Shadow, поиск продвигает
  Pandaolate;
- разрешена и SEO-роль shadow: книга доступна на обоих сайтах, но основной
  дубликат Pandaolate **после отдельного решения и проверки** получает noindex;
- скрыта/заблокирована/удалена: Shadow не показывает книгу вне зависимости
  от прежнего разрешения или SEO-роли.

## 3. PostgreSQL-проекция

Миграция 202610280007 создаёт:
- shadow_public_books: только вручную разрешённые **опубликованные,
  незаблокированные и неудалённые** книги;
- shadow_public_chapters: опубликованные, не заблокированные, не удалённые и
  уже наступившие по времени главы разрешённой книги, **только метаданные**
  без body_markdown, приватных редакций и кошельков;
- индексы для ограниченного чтения и правила непротиворечивости SEO-выбора.

Наличие **платной** главы среди опубликованных глав не исключает всю книгу
из Shadow — отдельное разрешение даёт владелец. Но текущая платная доставку
TOR использует приватный S3. В этих представлениях **нет текстов платных глав**.
Чтобы реально выдавать такую главу в Shadow бесплатно, понадобится отдельная
явная политика безопасного доступа к конкретной версии и проверка прав, а
не чтение закрытой версии из основного приложения без проверки. До этой
реализации никакой публичный URL Shadow не обещает выдачу такой главы.

Главная учётная запись tor_app по существующему контракту имеет доступ к
базовым таблицам и используется **только в основном TOR**. Миграция для новых
представлений явно отзывает DML-права tor_app и оставляет SELECT. Для будущего
Shadow требуется **отдельная** роль shadow_reader с доступом к подключению
к БД и SELECT только на эти представления, без SELECT на books, chapters,
chapter_versions, wallets, users, purchases, без DML и без CREATE/USAGE к
ненужным схемам. **Миграция роль не создаёт:** у tor_migrator нет CREATEROLE.
Роль и пароль создаются отдельным проверенным операторским bootstrap-процессом
и должны пройти отрицательные проверки в PostgreSQL перед запуском сайта.

## 4. Роутинг и правила поисковой видимости (будущая интеграция)

Только после реального развёртывания двух отдельных веб-процессов:
- основной домен: pandaolate.ru, отдельный настраиваемый Shadow origin из
  уже принадлежащих владельцу доменов;
- для выбранной индексируемой книги: одна индексируемая версия на стороне
  seo_index_owner, вторая читабельная версия с noindex,follow;
- каждая индексируемая страница имеет self-canonical своего домена;
- сайты генерируют **свои собственные** robots.txt и sitemap.xml, в которых
  нет запрещённых/удалённых/noindex URL и ссылок другого домена;
- страницы с noindex должны быть доступны роботу для чтения директивы;
- известные индексируемые книги на Pandaolate **нельзя** массово переключить
  в Shadow; первые 10–20 книг для эксперимента выбирать вручную.

Исходный Python Shadow принудительно ставил canonical основного домена.
Этот подход сознательно не переносим. Гарантий принятия РСЯ, индексирования
или роста поискового трафика нет.

## 5. Приёмка этого среза

1. SQLx миграция на свежей и обновляемой базе; существующие книги имеют
   shadow_enabled=false, seo_index_owner=pandaolate.
2. SQL View: черновик, admin hold, удалённая книга не видны; после ручного
   включения обычная опубликованная книга появляется, после отключения
   исчезает; прямой запрос по ID также не раскрывает книгу.
3. Публикации: неопубликованные, отложенные и заблокированные главы не
   появляются в shadow_public_chapters; наличие платной главы не исключает
   выбранную книгу.
4. На роли tor_app представления доступны только для SELECT (ни INSERT,
   ни UPDATE, ни DELETE); подключение PgShadowCatalog::connect под tor_app
   запрещено. Отдельная роль shadow_reader — следующий этап.
5. Rust-unit: noindex для невыбранных страниц, Shadow SEO-owner только
   после отдельного решения, блокировки не продвигаются поисковиком.
6. Отсутствие изменений текущих страниц, покупателей, цен, каталогов,
   метрик и опубликованного VPS Pandaolate.

**Что пока не делаем:** новый домен/DNS, рекламный код РСЯ, массовый
noindex старых книг, изменение существующего главного reader, S3-раздачу
платного текста, миграцию пользовательского аккаунта. Всё это — отдельные
контролируемые этапы после приёмки кода.
