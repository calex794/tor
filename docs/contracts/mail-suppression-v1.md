# MAIL-01g1 — durable recipient suppression

The quota gate now checks recipient suppression before spending an attempt. Suppression applies to all outbound purposes and survives account deletion or service restart. It never blocks login or in-site support. Use only the HMAC recipient identifier already recorded in the immutable reserved attempt; do not store raw addresses, provider error text, IPs or message bodies. The existing singleton guard serializes new reservations and verified feedback; a worker must still recheck relevant eligibility just before SMTP. Already in-flight submissions cannot be recalled.

Only positively identified nonexistent recipients and authenticated spam complaints qualify. A generic permanent failure (including a provider policy block or sender authentication failure), temporary failure, timeout, delivery report or DNS error never creates a recipient suppression. The hard-bounce suppression expires 30 days after the correlated attempt (provisional conservative policy); complaint suppression has no automatic expiry and cannot be downgraded. Duplicate/older events do not extend a hard bounce. A reviewed reactivation flow and retention policy for complaints are separate acceptance gates. Cleanup of expired bounces is bounded, and the worker must schedule it later. Existing reservations are not refunded.

MAIL-01g1 provides the trusted internal API, NOT an externally authenticated callback. Only a reservation from the last 48 hours can be correlated at this stage; missing references are reported as Uncorrelated, not converted into a guessed recipient. MAIL-01g2 must provide durable provider-message correlation before submission, authenticated event ingestion with replay handling, and a longer bounded correlation lifetime for delayed delivery feedback. Real provider payload classification must be verified against current documentation before activation. No public callback, real provider calls, SMTP, or deployment.

Tests cover typed classification, missing attempt, duplicate feedback, hard-bounce expiry, complaint precedence, account deletion/recreation, restart, case normalization, blocking across purposes without quota consumption, and unaffected recipient. Existing Commerce shard runs mail_01_ tests; CI acceptance pending.
